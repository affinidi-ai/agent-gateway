## [1.0.2] - 2026-10-28

### Security

- **Update zstd-sys to 2.1.2 and ignore the zstd advisories no release fixes yet** — RUSTSEC-2026-0410 reports memory corruption in the zstd-sys WebAssembly allocator shim, fixed in 2.1.2, which Cargo.lock now selects. RUSTSEC-2026-0391, RUSTSEC-2026-0398 and RUSTSEC-2026-0403 affect zstd 0.13.3 and zstd-safe 7.2.4 and are fixed only in zstd 0.14 and zstd-safe 8, while pulsar and the Solana RPC client still require zstd 0.13. The gateway calls no zstd API itself, so they are ignored in .cargo/audit.toml with the reason until those dependencies move.
- **Stop reading task history for the managed agent's identity over Fabric** — Over Fabric, both gateways read the managed agent's identity from the first entry of a task's `history`, which is normally the caller's own message. A caller could have its self-asserted identity resolved as the agent's and signed, and the agent's credential could be attached to the caller's message. Task history is no longer read for identity on the Fabric path, matching a direct call.

### Added

- **Show the Trust Recorder status on identities and the recorder panel** — The Identities page now shows a Recorded, Partly recorded, Failed, Skipped or Not attempted yet chip for each managed agent whose surface has a Trust Recorder, with a tooltip naming the registry, the reason and the record counts, and a Recorder filter. The Trust Recorder panel shows a Last outcome row. The status is the recorder's last known outcome, kept per surface and agent, saved only when it changes, cleared when the surface is deleted or its Trust Recorder entries change, and follows live updates. It carries codes, counts and times only, never registry error text.
- **Retry the first call to a directory-listed mediator while its DID is refused** — For a mediator the mediator directory lists, which may admit a DID only after the directory's operator has registered it in response to the creation_started notification, when the first call of a new Connection Point to it is refused because it does not know the DID yet (an HTTP 403, an ACL denial, or the live connection not becoming active), the gateway repeats it with the same DID instead of failing at once. AG_MEDIATOR_DIRECTORY_FIRST_CALL_RETRY_ATTEMPTS (default 5, 0 to 20, 0 never repeats) and AG_MEDIATOR_DIRECTORY_FIRST_CALL_RETRY_DELAY_MS (default 2000) set the repeats and the wait, for directory-listed mediators only. A mediator the operator added, or one the directory no longer lists, is never retried and its refusal fails at once, and for an unlisted provided mediator the error says it is no longer offered by the directory. Only an HTTP 403, an ACL denial and the live connection failing to become active (which also covers an unreachable mediator) are repeated, other failures end creation immediately, cancellation stops the wait, the whole sequence is capped at 45 seconds, and after the last repeat creation fails as before. This lets a mediator that only admits known DIDs accept the DID once a receiver of the event hook has registered it. See docs/INTEGRATIONS.md.
- **List extra mediators from an operator-configured mediator directory** — When AG_MEDIATOR_DIRECTORY_URL is set, the gateway reads a list of mediators from that endpoint with a signed GET (the same X-Webhook-Timestamp and X-Webhook-Signature-256 scheme and AG_EVENT_HOOK_SECRET as the event hook, https unless the host is loopback, redirects not followed) and shows them in GET /v1/mediators, GET /v1/mediators/compatible, the Create Connection Point wizard (which pre-selects the first one) and the Mediators page. The endpoint answers {"items":[{"did","name"}]}, other fields are ignored. An unavailable, slow or invalid directory leaves only the stored mediators listed; right after start the gateway asks again every 2 seconds for up to 30 seconds, allowing each of those requests 10 seconds, without making any request wait, and an expired list is served at once while one background task refreshes it. Creating a Connection Point on a directory entry stores a provided mediator record for it under an id fixed by the DID before the Connection Point's first event, so every event carries the final mediator id (the record stays and is reused if the creation then fails; the final check and save hold the record's lock, and a token scoped to directory ids can create on the entry repeatedly). A mediator the operator added for the same DID is a separate row and is never used for the entry, and the entry is always listed under its directory id. Creating on an entry needs no mediators.edit permission and does not count toward the mediator limit. Creating a Connection Point on a directory id before the directory has answered successfully answers 503 with a Retry-After header instead of 404. A stored provided record cannot be edited through the API (409) and can be deleted only once the directory has answered without its DID and no Connection Point or pending pairing uses it (the record is stored only after the request's authorization and scope checks pass), which refreshes it; it follows the caller's mediator resource scope by its own id. The first-call retry also applies while the directory has not answered successfully yet, and each attempt is bounded by the 45 second cap. Mediator responses gain provided only when a directory is configured or a record was created from an entry. List requests never wait for the directory, even while it is down, and a provided record the directory stopped offering, or any provided record when no directory is configured, is marked deletable in the list. The first-call retry needs a configured directory, its delay is at most 30 seconds (a larger or invalid value falls back to the 2 second default), and a repeat only starts when at least 10 seconds of the 45 second cap remain after its wait, so a long delay means fewer repeats. Starting a pairing with a directory-provided acceptor mediator holds that record's lock while the pairing is stored. Each acceptance of an invitation now has its own pairing (keyed by its temporary connection point), so concurrent acceptances never overwrite or remove each other's state, and the connection-accepted message is matched to the pairing and the pending gateway of the connection point it arrived on, never to another acceptance's. When accepting an invitation fails after the pairing is stored, the pairing is removed together with its temporary connection point, pending gateway and generated keys. Finalizing a pairing validates the acceptor mediator and this attempt's pending gateway before any state is written (a pending gateway removed by a restart is no longer recreated, so an acceptance in flight during a restart does not complete), holds a provided acceptor mediator's lock, with the expiry and the record checked again under it, until the permanent connection point is saved, and finishes removing the temporary connection point and its keys even when stopping its listener aborts the running task. Once its expiry (oob_connection.pending_expiry_hours) has passed, neither a pairing nor a temporary connection point that names the record blocks deleting it, and an expired pairing cannot be finalized, and a pairing rebuilt from its temporary connection point keeps that connection point's recorded expiry (or its creation time plus the configured lifetime) instead of getting a new one. See docs/INTEGRATIONS.md.
- **Announce the DIDs of gateway pairing and Trust Registries to the event hook** — The gateway now sends the event hook the DID it generates for each flow that logs in to a mediator, not only for Connection Points created through the API. The acceptor's temporary and permanent DIDs, the inviter's permanent DID after approval, and the DID of a stored Trust Registry are announced before the gateway first contacts the mediator, so a receiver that registers DIDs on a mediator that admits only known DIDs, such as the shared public mediator, covers them. Their records now carry mediator_did, so deleting a pairing, expiring a temporary Connection Point or deleting a Trust Registry sends deleted. The acceptor's handshake DID and a new Trust Registry's DID also repeat their first mediator call while a mediator the directory lists refuses a DID it has not admitted yet. The ephemeral DID for querying an unstored public Trust Registry and connections rebuilt after a restart are not announced. See docs/INTEGRATIONS.md.

### Changed

- **Refuse to finalize a pairing whose own pending gateway is missing** — Finalizing a pairing, for every gateway and not only with a directory mediator, now needs the pending gateway of that acceptance and refuses, writing nothing, when it is missing. Earlier versions recreated it with no tenant, which could attach a gateway with no tenant to a tenant's mediator or pick up another acceptance's gateway by the shared DID. An invitation accepted just before the gateway restarts, which removes pending gateways left by an earlier run, therefore has to be accepted again. See docs/INTEGRATIONS.md.

### Fixed

- **Return the managed agent's identity credential for A2A 1.0 tasks over Fabric** — Over Fabric, the gateway in front of a Managed Agent did not find the identity the agent asserted on an A2A 1.0 task, because it did not read the task a `SendMessage` result wraps in `{"task": …}`. It issued no identity credential, and the calling gateway received the raw identity. Both gateways now read the same response locations as a direct call: the task's status message, then its artifacts. The credential is placed on the status message, and the calling gateway finds and verifies it there. The calling gateway does not read artifacts, so an identity or credential found only in an artifact is ignored.

## [1.0.1] - 2026-10-26

### Breaking

- **Migrate existing integrations to endpoints and event sets on upgrade** — On its first start the Active node turns each integration into an endpoint, an event set of the events it received and an integration, with the same id, writes _storage/integrations/migration-report-<unix seconds>.json and renames the old directories to <dir>.migrated-<unix seconds>, deleted 30 days later as they may hold plain-text credentials. Upgrade both nodes of a pair before the Active node starts; a Standby migrates when promoted. Attachments to some gateways or connection points now receive every resource's events, every tenant's included. Tenant-owned integrations become appliance-wide and are written disabled, since enabled they would receive every tenant's events; review each before enabling it. Custom _ variables and unfilled placeholders leave the templates, and endpoints failing the current checks are written disabled; the report names each change. The old paths resolve against the config file's directory, and while storage_paths.integrations is set, the new integration paths a config leaves unset go beside it, so a config written for the previous version needs no change; set them before removing the old keys. See the INTEGRATIONS upgrade section.
- **⭐ Manage integrations as an endpoint plus an event set** — /v1/integrations now keeps integrations that join one endpoint (/v1/integrations/endpoints: transport, destination, credentials) and one event set (/v1/integrations/event-sets: events picked from the whole catalog), with the template on the integration. Categories and tenant owners are gone.

### Security

- **Upgrade rustls-webpki and webpki roots to clear three distrust advisories** — rustls-webpki 0.103.15 could accept certificates through distrusted intermediates (RUSTSEC-2026-0382), and webpki-roots and webpki-root-certs 1.0.8 still trusted distrusted emSign intermediates (RUSTSEC-2026-0381, RUSTSEC-2026-0383). They are now 0.103.16 and 1.0.10, and the dependency audit passes again.
- **Keep secret values and webhook URLs out of integration errors** — Saving an endpoint, test sends, the startup definition check and the migration report no longer show the value of a referenced secret or a URL, such as a Slack webhook URL. A failing $SECRET: reference is reported by field and secret id only, URL validation messages name the host but never the URL, and Redis stream errors no longer repeat part of the Redis URL.
- **Render dashboard notifications as text, not HTML** — Dashboard toasts built their message and action label as HTML, so a name or server error message containing markup, such as an integration endpoint name, could run script in the browser of whoever saw the toast. Toasts now show all text literally.
- **Document that integrations.edit can use and read every appliance secret** — An endpoint's $SECRET: reference is resolved by the gateway when it sends, without a secrets permission, so whoever holds integrations.edit can point an endpoint at a host of their choosing, send a test and receive the secret's value. Grant integrations.edit only to roles that may read secrets; the defaults keep it and secrets.* administrator only. Tenant-owned secrets never resolve for endpoints. RBAC.md and INTEGRATIONS.md say so.
- **Escape event values in HTML integration emails** — Values filled into an HTML email body have &, <, >, " and ' escaped, so caller-supplied text such as a user name cannot add markup or links to the message. The template itself is not escaped.
- **Never return integration endpoint credentials from the API** — SMTP passwords, Slack webhook URLs, webhook signing secrets and headers, and stream SASL passwords, Redis URLs and Pulsar auth tokens are write-only: responses name the secrets set but never their values, so the user role's integrations.view no longer reveals credentials.
- **Refuse tenant and resource-scoped tokens on the integrations API** — Integrations, endpoints and event sets belong to the whole appliance, so every /v1/integrations route answers 403 to a tenant or resource-scoped access token.
- **Apply the response policy and identity credential to A2A streams** — An A2A event stream from a direct Target used to be returned whole, and the response checks found no JSON in it. A response policy rule on the content could not block a stream, the response extension rules were skipped, and the caller received the agent's raw, unverifiable identity instead of the signed agent-identity-credential. Each event is now checked before it is sent and its identity claim replaced by the credential. On a surface that reads identity from the response, a stream that never claims one ends with an identity error. fabric:// surfaces and Transit Points still return the stream whole without these checks.
- **Update ctutils to 0.4.5 so its comparisons run in constant time** — ctutils, which the gateway's elliptic-curve signing and DIDComm libraries use, could compile its mask generation and 128-bit comparisons to code that branches on the values compared, which can leak them through timing. The RustCrypto advisory is fixed in 0.4.4; the lockfile now pins 0.4.5.
- **Keep payment configuration errors out of 500 responses** — When MPP challenges cannot be generated, or x402 payment requirements cannot be serialized, the 500 response says only "Payment configuration error" and the detail is logged. Before, the response carried the internal error text.
- **Build the dashboard with Node.js 22.23.4 to fix CVE-2026-111497** — The Docker images and the CI frontend job built the dashboard with Node.js releases affected by CVE-2026-111497, an out-of-bounds write in the Brotli decoder. They now use Node.js 22.23.4, the patched 22.x release; the CI job moves off Node.js 20, which no longer receives fixes.
- **Update dependencies with published security fixes** — Updates anyhow to 1.0.104 and event-listener to 5.4.2 to fix soundness advisories RUSTSEC-2026-0190 and RUSTSEC-2026-0221, and applies non-breaking dashboard dependency fixes, including the critical websocket-driver, shell-quote and proxy-addr advisories in the build toolchain. Overrides pin postcss-selector-parser to 7.1.6 or newer and @tootallnate/once to 2.0.1 or newer, clearing GHSA-rj75-hqrm-r3gf and GHSA-vpq2-c234-7xj6 from the build.
- **Upgrade the dashboard to React Router 7.18.4** — React Router 6 is affected by GHSA-wrjc-x8rr-h8h6, an open redirect through a backslash in Link and useNavigate targets, and GHSA-337j-9hxr-rhxg, with no 6.x fix. The dashboard now uses React Router 7.18.4, leaving no known advisories in its production dependencies.
- **Upgrade Alloy to 2.5 to drop the unsound lru 0.16 dependency** — Alloy 1.x and 2.1 depend on lru 0.16, which is affected by RUSTSEC-2026-0253, a potential use-after-free in LruCache::pop. The gateway and its x402 payment dependencies now share Alloy 2.5, which uses the patched lru 0.18.
- **Build the dashboard on Node.js 22.23.4** — The Docker images now build the www dashboard on Node.js 22.23.4 instead of 22.21.1, and the MCP conformance CI job pins the same version. 22.23.4 is the October 2026 Node.js security release, which fixes an out-of-bounds write in the Brotli decoder (CVE-2026-111497) and several TLS certificate hostname-check bypasses. Node only runs while the image is built; the runtime image ships no Node.
- **Update TLS certificate dependencies in Cargo.lock** — Bumps rustls-webpki to 0.103.16 (could accept distrusted intermediates, rustls/webpki#546), and webpki-roots and webpki-root-certs to 1.0.10 (bundled roots trusted distrusted emSign intermediates, rustls/webpki-roots#133). Fixes the failing Rust dependency audit.
- **Update rustls-webpki and webpki roots to reject distrusted emSign intermediates** — Bumps the transitive rustls-webpki dependency from 0.103.15 to 0.103.16 and webpki-roots and webpki-root-certs from 1.0.8 to 1.0.10. The older versions could accept certificate paths through distrusted emSign intermediates whose private keys are now publicly known (RUSTSEC-2026-0381, RUSTSEC-2026-0382, RUSTSEC-2026-0383). Restores a passing cargo audit.
- **Update ctutils to 0.4.5 for constant-time mask and comparison fixes** — Bump the transitive ctutils dependency from 0.4.2 to 0.4.5, which fixes non-constant-time mask generation and u128 comparisons reported by cargo audit (RustCrypto/utils#1569). The crate is pulled in by the elliptic-curve and digest crates used for DID and DIDComm cryptography.
- **Update crypto-bigint to 0.7.10 for constant-time operation fixes** — Bump the transitive crypto-bigint 0.7 dependency from 0.7.5 to 0.7.10 (and ctutils to 0.4.6), which fixes timing variability in operations intended to be constant-time (RUSTSEC-2026-0387). The older 0.3 and 0.5 copies pulled in by elliptic-curve 0.13 and der 0.5 have no fixed release, so the advisory is recorded as accepted for them until those upstream crates move to 0.7.

### Added

- **Check that pull request titles follow Conventional Commits** — Squash merges use the pull request title as the commit message on main, so a new pr-title workflow checks the title with the Validate PR title job and fails when it does not follow Conventional Commits, for example feat: or fix(ci):. The description after the type must be at least 5 characters, the same minimum as the organization commit message rule. The job runs again when the title is edited, so fixing a title clears the failure without a new push.
- **⭐ Manage integrations, endpoints and event sets from one Integrations page** — The Integrations page has three tabs. Endpoints show the fields of their type, keep stored secrets hidden and can point a secret field at a stored secret. Event sets pick events from the whole catalog with search. The integration editor joins an endpoint and an event set, writes the template with the event set's variables, sets the audit delivery limits when audit events are picked, and sends a test as it stands. Endpoints and event sets in use name their integrations instead of being deleted.
- **Send test messages through an endpoint or an integration, saved or not** — POST /v1/integrations/endpoints/{id}/test sends the endpoint's default message, POST /v1/integrations/{id}/test sends a saved integration's message for one event of its event set with sample values, and POST /v1/integrations/test does the same for an integration not saved yet. A failed send answers 502 with the reason.
- **Give every integration message the event's name, summary and data** — Templates can use EVENT_NAME, EVENT_SUMMARY (one line on what happened) and EVENT_DATA (the event's values, or the audit record, as JSON). For webhook and stream endpoints a field that is exactly ${EVENT_DATA} or ${AUDIT_RECORD} embeds the JSON object; Slack and email send it as text. A template that leaves fields out gets the endpoint type's defaults, so an empty template sends a complete message.
- **List every event integrations can deliver in one catalog** — GET /v1/integrations/catalog lists every delivered gateway, user, connection point, x402, MPP and Governance Audit event with its family, audit group and the template variables its delivery fills, plus the placeholder syntax and each endpoint type's secret fields.
- **Reference stored secrets from integration endpoints** — An endpoint secret field may hold $SECRET:<secret_id>, resolved from the appliance-wide secrets store at each delivery, so one credential can serve several endpoints.
- **⭐ Stream A2A responses event by event on surfaces with a direct Target** — When a direct A2A or AP2 Target answers SendStreamingMessage (message/stream) or SubscribeToTask (tasks/resubscribe) with text/event-stream, the gateway now forwards each event as it arrives, in order, instead of reading the whole stream and returning it at the end. Each event gets the checks a non-streaming reply gets: an identity claim is resolved and replaced by the signed agent-identity-credential, response custom metadata is added, and the response extension rules and response policy run on it. The agent identity the first claim resolves holds for the whole stream, and an event that resolves another ends it with identity_changed. The Trust Recorder records the agent only once an event that resolved it passes these checks, and one allow decision of the response policy is audited per stream. An event that fails a check is not sent; the stream ends with a JSON-RPC error event whose data.code names the cause, since the status has already been sent. The stream closes when the Target closes it, so terminal and interrupted task states reach the caller as sent. On a surface that reads the agent's identity from its response, a stream that delivers results without any event claiming that identity ends with an identity_extension_missing error event after its last event, since a non-streaming reply without a claim is refused. A slow caller slows the Target instead of filling a buffer. fabric:// surfaces and Transit Points still buffer the stream.
- **Bound A2A event streams with the new [a2a] stream_max_lifetime_secs** — A forwarded A2A event stream may run for [a2a] stream_max_lifetime_secs (default 3600, 1 to 86400), no longer the 30-second request timeout, though the Target must still send its response headers within the request timeout. A streaming call is sent once, whatever the surface's retry policy. A Target that sends nothing for the surface's networking.timeout.idle_secs ends the stream, as the Surface Builder's Idle timeout help now says, and one event may hold up to [a2a] max_body_size; a stream that passes a limit ends with an error event.
- **Notify a receiver of Connection Point events through an event hook** — When AG_EVENT_HOOK_URL is set, the gateway POSTs JSON events to that endpoint for each Connection Point - connection_point.creation_started (DID minted, before the first mediator contact), created, creation_failed (also when the request is cancelled), connected (first mediator connection of each listener start) and deleted (when a record is deleted through the store, which covers the API delete and expiry cleanup; deleting a gateway does not delete its User Connection Points, so nothing is sent for them). Each event is delivered from its own background task and never delays or fails the request; it is retried like an integration publish (five retries after about 1, 2, 4, 8 and 16 seconds, including on 401 and 403) and then dropped, and a permanent 4xx or a 3xx redirect (never followed) is logged and dropped. Lifecycle events and connected use separate delivery pools so a restart burst of connected cannot starve them. Nothing is persisted, so events not yet delivered are lost on restart. AG_EVENT_HOOK_SECRET (at least 32 characters, plain or an env://, file:// or aws_secrets:// reference) signs calls with X-Webhook-Timestamp and X-Webhook-Signature-256 when it is set, and AG_EVENT_HOOK_TIMEOUT_MS (default 5000) bounds one attempt. The hook URL must be https with AG_EVENT_HOOK_SECRET set; http is accepted only for a loopback host (localhost, 127.0.0.0/8 or ::1), and only a loopback receiver may go without a secret, otherwise the hook is disabled with an error log. Only Connection Points created through the management API after the gateway recorded mediator_did are announced; pairing flows and older Connection Points are not. creation_started and creation_failed exist only once the DID is minted, and creation_failed carries no reason. connected fires on a listener's first connection after each start, and every restart re-announces live Connection Points. Delivery order across events is not guaranteed, so receivers must order by the clock-seeded sequence (best-effort across restarts, since a backwards clock step can lower it) and be idempotent. sequence is for ordering only, because the clock reseed after a restart can skip numbers, so receivers must not treat gaps as errors. connected is built from the stored record at the time it is sent and is skipped when the record was deleted meanwhile. A stored Connection Point now records the mediator_did it was created on. See docs/INTEGRATIONS.md.
- **Warn when a Trust Recorder uses the surface Issuer but none is selected** — A Trust Recorder entry whose Authority is Use surface Issuer is skipped, and writes no records, when the surface has no Issuer or its Issuer no longer exists, and the only sign was a gateway log line. The Trust Recorder panel and the entry in its editor now show a warning while the surface has no Issuer selected, or its Issuer was deleted, pointing at the Surface's Issuer setting. Entries with an explicit Authority are not affected and show no warning.

### Changed

- **Deliver every event to the integrations whose event set holds it** — Gateway, user, connection point, x402 and MPP events go to every active integration with an active endpoint whose event set holds the event, from every resource, and Governance Audit records go to every integration whose event set holds their audit event. A placeholder with no value now renders empty instead of staying in the message.
- **Guard the Integrations pages with the integrations permissions** — The Integrations sidebar item and pages need integrations.view, the editors and test sends integrations.edit and deleting integrations.delete, instead of the MCP proxy permissions. The editors move to /integrations/new and /integrations/{id}, and the Audit page's Forward records starts an event set of every audit event.
- **Manage Governance Audit forwarding with the integrations permissions alone** — Every /v1/integrations route checks only integrations.view, integrations.edit or integrations.delete, and all events are handled the same: event sets holding audit events, the integrations delivering them and their endpoints are listed, read, changed, deleted and test-sent like any other. Before, callers without audit.view did not see audit integrations and could not change them. audit.view still guards the audit records themselves. Every integrations.view holder, the user role by default, now sees every endpoint's destination, the Governance Audit one included (secret fields are never returned). See RBAC.md.
- **Share webhook signing between integrations and the event hook** — Real webhook integration deliveries, the dashboard's Test notifier action and the event hook now compute the X-Webhook-Signature-256 value through one shared function. Signatures are unchanged.
- **Expand Policy Instructions & Examples from anywhere on its header** — On the Create Policy Definition page the instructions panel opened only from its small arrow button, so users missed the examples. Clicking the title, icon or empty header space now expands and collapses it, the title stays a heading with a full-width button inside it, so screen readers still announce it and Enter or Space toggle it, and the arrow flips to show the state and stays as the visual hint.
- **Explain how Issuer, Authority and Entity relate in the Trust Recorder** — The Trust Recorder editor has a collapsed explainer for Authority, Entity, the entry Issuer and the surface Issuer, with a link to the Trust elements guide. The Issuer field no longer says it signs the records, because it is only recorded as the Entity of custom records whose Entity Target is Issuer DID.
- **Report refusals as typed errors instead of prepared responses** — Consent ticket checks, credential provider reference checks, token refresh storage and the fabric sender, envelope, policy and Target body checks now return an error that names why a request was refused, and the response is built from it in one place. The statuses and bodies callers receive are unchanged. Clippy 1.98 no longer flags these functions for returning a large error.
- **Build x402 and MPP payment refusals from typed payment errors** — x402 and MPP payment checks return the challenge to pay or why a payment failed, and the 402 or 400 answer is built from it on the proxy and fabric paths alike. A request with no payment credential gets its 402, x402's, MPP's or both combined, from one shared builder instead of four copies. The answers clients receive are unchanged.
- **Move the A2A proxy version notes to the A2A proxy's Agent Card tab** — The Managed Agent panel no longer shows the A2A version and identity notes when its Target is an A2A proxy. The A2A proxy's Agent Card tab now gives a shorter explanation: the card lists the versions the exposing surface accepts, as its Access Point shows them; a new surface whose Target is the proxy accepts only A2A 1.0, so its callers send the A2A-Version 1.0 header and use A2A 1.0 methods such as SendMessage; and requests to the proxy are checked only for the JSON-RPC envelope.
- **Remove the "unverified" badge from Agent Card names in Identities** — The Identities page no longer shows an "unverified" badge beside a caller's Agent Card name or a managed agent's target Agent Card name. The names are still self-asserted and are still never signed into the identity VC or published to Trust Recorder context or trust registries. Verified agent names keep their verified marker.

### Fixed

- **Report stored integration definitions that fail their checks at startup** — Each node checks the stored endpoints, event sets and integrations when it starts and logs a warning for each that fails, such as an endpoint whose secret is missing after a restore or an integration whose event set is gone, plus a summary with the counts. Nothing is changed.
- **Refuse to delete a secret an integration endpoint references** — Deleting a secret that an endpoint's secret field or webhook header names as $SECRET:<secret_id> left every delivery to that endpoint failing. The delete now answers 409 naming the endpoints, and the Secrets page shows why a delete failed.
- **Deliver an event to each integration without waiting for the others** — The integrations of one event were delivered one after another, so an endpoint that was slow or unreachable, retrying for up to 30 seconds per attempt, delayed every other integration of that event. Each integration is now delivered on its own.
- **Share one Kafka producer per endpoint** — Kafka producers were kept per integration, so every test send built a new client with its own broker connections, and integrations on one endpoint each held their own. The producer now belongs to the endpoint and is dropped when the endpoint is changed or deleted.
- **Stop a VP Audit Log write from landing after the audit pipeline stops** — A write cancelled while the pipeline stopped could still land afterwards, after the next pipeline had read the log's recent event ids, so the record was written twice after a step-down and restart. Stopping now waits for that write or refuses it, so the record is written once.
- **Refuse webhook headers and methods an endpoint cannot send** — Webhook headers that are not an object of strings, including a $SECRET: reference as the whole field, headers the gateway sets itself (Content-Type, X-Webhook-Timestamp, X-Webhook-Signature-256) and methods other than POST, PUT and PATCH are refused when the endpoint is saved. A stored endpoint with one of those headers sends it once, with the gateway's value, instead of twice, which broke signature checks and body parsing.
- **Keep carried-over A2A settings when a stored surface change is applied** — A stored surface that reached the gateway as a storage event, from another node's write, the cache refresh scan or the disk refresh a configuration reload starts with, was applied as stored. An A2A surface stored without its own settings was then served with the defaults (0.3 and 1.0), even when the reload running at the same time had just given it A2A 1.0 only from the retired a2a_legacy_compatibility flag, so callers without an A2A-Version header were accepted. The record is now given its settings in memory before it is applied, as a load gives them; applying the event writes nothing back to storage.
- **Stop counting a slow caller's reading time as an idle MCP stream** — The idle timeout of an MCP text/event-stream passthrough ran from the moment the previous chunk was handed on, so a caller that took longer than mcp_http.stream_idle_timeout_secs to read an event ended the stream as idle even though the upstream kept sending. The timeout now counts only the time the gateway waits for the upstream, for MCP and A2A streams alike.
- **Stop a deleted Connection Point from reappearing after deletion** — A listener shutting down while its Connection Point was being deleted could write its runtime status back and recreate the record, which then counted against the appliance limit and was reloaded at restart. The listener's status write and an invitation's redeem and release writes now happen only while the record still exists, so none of them recreates a deleted record. The store's create, update and delete calls for one Connection Point id are serialised against each other.
- **Apply configuration reloads and surface changes one at a time** — A configuration reload re-reads Agent Surfaces from disk, and each surface that changed is then applied again as a single-surface change. That change could run while the reload was still applying its own, so a surface edited by hand and reloaded could keep serving the A2A versions it had before the reload. Explicit reloads, the reload a node runs when it becomes Active, API surface changes and changes from storage are now applied one at a time, and a change from storage applies the surface as currently stored rather than an older copy.
- **Persist system metrics every 15 minutes and on shutdown, not every 5 seconds** — The CPU and memory history behind the dashboard system metrics view was rewritten in full to _storage/system_metrics/system_metrics.json after every 5-second sample. Once the 24-hour buffer filled, each instance rewrote about 3.8 MB twelve times a minute (about 65 GB a day), which is costly on network-backed storage billed per GB written. Samples are still collected every 5 seconds and served from memory, but the history is now written at most once every 15 minutes and again when the gateway receives SIGTERM or Ctrl-C, via a temp file and rename so a crash mid-write can no longer leave a truncated file. SIGTERM and Ctrl-C now stop the gateway promptly with exit code 0 instead of waiting to be killed; each shutdown step is limited to 10 seconds and in-flight requests are not drained. A crash, forced kill or rolling deploy can lose up to 15 minutes of history. Temp files from failed or interrupted writes are removed, either right away or at the next startup.
- **Stop trust registry reconnects from leaving duplicate mediator sessions** — Reconnecting a trust registry, from the dashboard, at startup or after a stale connection, left the previous connection's mediator websocket running. It kept reconnecting under the same DID and fought the new connection, so the mediator closed one with "A new duplicate websocket connection for this DID" and the trust registry ended up Failed. Replaced and removed connections are now shut down, including when the gateway steps down to Standby, and stale connection recovery reuses a connection another request has already replaced instead of tearing it down. A connection setup that fails partway also closes its websocket. A reconnect or connection setup now closes the current connection before opening the new one, so the old connection no longer receives the duplicate error and marks the trust registry Failed. A stale temporary connection to a public trust registry is replaced with a new one instead of staying stuck, and closing a connection no longer waits more than 10 seconds for its websocket to shut down.

### Removed

- **Remove integration tabs from gateway, connection point, user and identity pages** — An integration receives every event of its event set from every resource, so the dashboard no longer attaches integrations to gateways, connection points, users or identities, and the connection point wizard has no integrations step.
- **Remove integration categories and custom variables from gateway.json** — The integration section keeps only variable_pattern and variable_pattern_description; categories, their variable lists and custom_variable_prefix are gone, and storage_paths.integrations and storage_paths.integration_triggers are replaced by integration_endpoints, integration_event_sets and integration_definitions. The two old keys are still read, with a deprecation warning, only to migrate from them.
- **Stop reassigning integrations to tenants** — Integrations belong to the whole appliance, so the tenant ownership API refuses the integrations kind with 400 instead of moving one to a tenant.
- **Remove per-resource integration attachments** — /v1/gateways/{id}/integrations, /v1/users/integrations and /v1/identities/integrations are gone, and connection points no longer take integration_id, integration_variables or integrations. An integration receives every event its event set holds, from every resource, and custom _ variables are gone with the attachments that held their values.
- **Remove the integration trigger, config and runtime-variables routes** — /v1/integrations/{id}/trigger and /v1/integrations/trigger-multiple, GET /v1/integrations/config and /v1/integrations/runtime-variables are gone; GET /v1/integrations/catalog lists the events, template variables and endpoint types instead. POST /v1/integrations/test now takes an integration that joins an endpoint and an event set.

## [1.0.0] - 2026-10-20

### Breaking

- **⭐ Stop checking the A2A request shape by default** — The A2A request-shape check (messageId, role, parts, params.id) used to run on every managed-agent A2A surface by default. A surface stored without its own settings now gets envelope validation (or off when [a2a] validate_messages is false), never the request-shape check, so malformed A2A messages are forwarded for the agent to decide. To keep refusing them, set Message validation to Envelope + A2A fields (access_point.a2a.validation = full) on those surfaces. On the first start after the upgrade, a warning names the surfaces that lost the check.
- **⭐ Record only the audit events each destination selects** — The VP Audit Log and each Governance Audit integration now record only the audit events selected for them, and nothing is selected by default. After upgrade, the VP Audit Log keeps policy decisions, trust checks and VP injections only if they were enabled before; credential delegation, payment and trace-termination records, which were always written, stop until selected in Settings › VP Audit. Existing Governance Audit integrations receive nothing until events are listed in their audit_events.
- **Deliver governance audit records at least once from a durable journal** — Audit records are journalled to disk before any destination receives them, and each destination reads the journal from its own position, so a slow or unreachable integration falls behind instead of losing records, and delivery resumes after a restart. A record may be delivered more than once; deduplicate on event_id. Integrations no longer depend on the VP Audit Log keeping a record. The journal lives in the audit log directory under journal/, and a crash loses at most the last batch not yet synced to disk. While the journal cannot be written up to 10,000 records wait in memory; beyond that the oldest are discarded and counted in agent_gateway_audit_records_lost_total with reason journal_write. The journal size is reported in agent_gateway_audit_journal_bytes and logged as a warning above 256 MiB; above 1 GiB the destinations still holding back its oldest part are moved past it, and what each skips is counted in agent_gateway_audit_sink_skipped_total with reason backlog_cap. The VP Audit Log never writes the same record twice. A record no destination selects is not built at all, so unselected events cost nothing, including the signed VP a consent-granted record may carry.
- **Store VP Audit selections as audit_events instead of audit_categories** — The settings API takes and returns audit_events, a list of event names such as policy_decision, and rejects names that are not audit events. A request that still sends audit_categories gets 200 and the field is ignored; send audit_events instead. Settings stored with audit_categories are read as the matching events (policies as policy_decision, trust_checks as trust_check, identity as vp_injected), so existing selections are kept.
- **Remove the dropped result from agent_gateway_audit_forward_total** — Records are no longer dropped from a full forwarding queue, so agent_gateway_audit_forward_total no longer reports result dropped, and integration_id is never empty. Alert rules on result dropped never fire; alert on agent_gateway_audit_sink_skipped_total and agent_gateway_audit_records_lost_total instead.
- **Answer full Fabric stream caps on the receiving gateway with capacity_reached** — A full framed-stream cap, Open replay table or table share, a full admission pool, or a peer past its Open rate, is now refused with capacity_reached instead of unavailable, so the sending gateway's caller gets 429 with Retry-After instead of 502. A 1.0.0 sender cannot parse capacity_reached, so while a pair runs mixed versions its callers wait for their response deadline, holding its stream slots, whenever the upgraded receiver is out of room. Normal traffic is unaffected. Upgrade both gateways of a pair together, or the sending gateway first, as an upgraded sender understands both codes.
- **⭐ Refuse did:web and did:webvh on private hosts unless allow_private_hosts is on** — DID resolution now refuses a host that is, or resolves to, a loopback, private-network, carrier-grade NAT or link-local address, and does not follow redirects; each method also refuses some local names outright. This closes an SSRF path through attacker-supplied DIDs and applies to every resolver the gateway builds. A stored mediator document is served from cache only until the resolver's TTL expires, so a stack whose mediator or peer DIDs live on such hosts must set the startup-only `[did_cache] allow_private_hosts = true`, which logs a warning at startup and also reopens cloud metadata. `scripts/_prepare.sh` turns it on for local and Docker dev stacks, and the BDD configs turn it on too.
- **⭐ Newly paired Remote gateways reach no surface until one is exposed** — Every pairing path, including the inbound handshake, now creates the peer with exposure mode `none`, so it can neither forward to nor list any local surface until an operator exposes one. An exposure update without `exposure_mode` and with an empty list now means `none`, not every surface. The capability query now filters on the authenticated sender's exposure and returns nothing when that lookup fails, instead of every surface.
- **⭐ Never apply tool-scoped credential bindings on Transit Points** — A legacy MCP request through a Transit Point matched `required_for.tools` against the JSON-RPC method, so a binding that listed a tool never applied there, while one that listed a method such as `tools/call` or `message/send` did. A `2026-07-28` `tools/call` matched on the tool name. Transit Points now apply only `all` bindings. Bindings carry no destination, and a partner upstream names its own tools, so a tool name that collided with one of the Target's tools would hand the partner a credential meant for the Target. `all` bindings still reach every Transit Point of the surface, including the `transit_credentials` that a surface without `outbound_credentials` reads as `all`. Access Points are unchanged. Upgrade note: a binding that lists a JSON-RPC method, or a tool called through a Transit Point with `2026-07-28`, no longer sends its credential to the Transit upstream. Use an `all` binding only if every Transit Point's upstream should receive it.
- **Refuse MCP requests that skip POST admission by method** — MCP admission, including the batch and single-object checks, ran only for POST. A PUT or PATCH, or a GET or DELETE with a body, reached the upstream without them, so an upstream that routes by path whatever the method could run a batch or a gated tool. Access Points, Transit Points and Fabric receive now answer 405 with `Allow: POST, GET, DELETE, HEAD, OPTIONS` to any method but those five, and 400 with JSON-RPC `-32600` to any non-POST request with a body. A standalone MCP Proxy answers DELETE with 405 and `Allow: POST, GET, HEAD`. GET and DELETE without a body behave as before. Upgrade note: an MCP client that sends PUT, PATCH or a body on GET or DELETE is now refused, as is an MCP POST whose body is not valid JSON or is JSON but not an object, on Access Points, Transit Points, Fabric receive and the standalone MCP Proxy.
- **Stop sending delegated credentials over Fabric unless the route opts in** — After upgrade, `fabric://` Targets and Transit Points on surfaces with `outbound_credentials` stop sending delegated access tokens to the peer, because the new `fabric_delegated_credentials` setting defaults to off and no migration turns it on. Turn the setting on for each Target or Transit Point whose peer relies on receiving the token, including `fabric://` Transit Points that rely only on their own `transit_credentials`. This includes A2A surfaces whose `fabric://` Transit Points sent the token as a header; A2A Access Point traffic over Fabric never carried it and is unchanged. Transit Points on surfaces without `outbound_credentials` also stop receiving other Transit Points' `transit_credentials`; give each one its own binding if it needs a token. The surface's Target on such a surface also stops receiving Transit Points' `transit_credentials`; add the binding to `outbound_credentials` if the Target needs it.
- **Apply mcp_http Origin and size limits to every MCP endpoint** — `mcp_http` Origin allowlist, header budget and `max_request_bytes` (default 1 MiB) now apply to every MCP endpoint and to `2024-11-05` traffic as well, so legacy browser clients whose Origin is not allowed get `403`, and oversized requests get `413`/`431`. Before upgrading, add browser origins to `mcp_http.allowed_origins` and raise `max_request_bytes` / `max_header_bytes` on endpoints that need them. Public endpoints given as bare listen addresses are skipped by the Origin check; any other public endpoint that is not an HTTP(S) origin is skipped with a warning.
- **⭐ Admit MCP 2026-07-28 on every MCP endpoint and retire mcp_protocol_mode** — Access Points, Transit Points, MCP Proxies and Fabric framed streams now admit MCP `2026-07-28` alongside `2024-11-05` without configuration, instead of rejecting it with `400` / `-32022` unless the endpoint was set to `dual`. `mcp_protocol_mode` is retired: stored records and API payloads that carry it still load, the value is ignored, it is dropped on the next save and no longer returned. There is no per-endpoint opt-out, so a modern request to a legacy-only upstream gets `502`. Buffered Fabric `ForwardRequest` stays `2024-11-05`-only.
- **Stop sending target credentials for failed callers over MCP proxy and Fabric** — Backends behind `proxy://` MCP, `a2a-proxy://` or Fabric surfaces with source authentication now receive requests from failed callers without the target credential, and will usually reject them. Two Fabric gateways that both require source authentication on the same header now reach the backend without the target credential, because the sending gateway strips that header; require caller authentication on one side of the hop or use a different header on each side (see docs/POLICY.md).
- **Refuse tenant token edits to records that belong to no tenant** — Tenant automations that updated, deleted or triggered appliance-wide records, including records created before tenant stamping, now get 403, and tenant tokens can no longer create Connection Points. Use an appliance-wide token, or have an operator assign the record with `PUT /v1/tenant-ownership/...`.
- **Pair one gateway per invitation and recreate invitations made before upgrade** — Each gateway invitation now pairs a single gateway; create a new invitation for every peer, including after rejecting a request. Invitations created before this release recorded a different invitation message id and are refused, so create them again.
- **Stop starting when the JWT verification strategy store cannot be opened** — A gateway in Active or Standby mode now exits at startup if its JWT verification strategy store cannot be opened, even when no surface uses caller authentication. Before upgrading, check that the gateway user can create and read the `jwt_verification_strategies` directory next to the secrets storage directory.
- **Publish Docker Compose ports on 127.0.0.1 instead of every interface** — A gateway started with docker-compose.yml is no longer reachable from other hosts on ports 8443 and 8080. Remove the 127.0.0.1 prefix in docker-compose.yml to expose it deliberately.
- **Require the payment requirement in fabric x402 verify-requests** — In `fabric_gateway` verification mode the requesting gateway sends its resolved requirement as `payment_requirement`, and the facilitator gateway verifies against it and rejects a verify-request without one. Upgrade requesting gateways first; an upgraded facilitator rejects every verify-request from a requester on an earlier build.
- **Accept no x402 payment on a surface without payment requirements** — A surface with x402 enabled and an empty `payment_requirements` list, or a requirement whose `amount` is not a number (such as one created from the x402 Payment Wall template before an amount is set), rejects every payment.
- **Take x402 signature-check fields from the configured requirement** — Clients no longer supply the transfer method or EIP-712 domain. For signature checks, an `eip3009` requirement needs `extra.assetTransferMethod`, `extra.name` and `extra.version`, and a `permit2` requirement needs `extra.assetTransferMethod`. A client must echo the issued requirement, including those fields, and an `upto` payment must authorise exactly the configured amount, as must every signed authorization.
- **Refuse SPL token requirements on Solana transaction-hash verification** — Solana transaction-hash verification checks native SOL lamports only, so a requirement for an SPL token is refused there and must use the `spl_transfer` method. A transaction that is not JSON-encoded is refused rather than checked without its recipient.
- **Require token_name and token_version for the EIP-3009 x402 test endpoint** — The x402 test endpoints issue and verify one requirement built from test-endpoints.json. `/protected` (EIP-3009) needs the new optional `token_name` and `token_version` fields in the `evm` entry, since the EIP-712 domain is no longer taken from the client.

In the plain log format the value is now double-quoted, for example token_id="agat_...", so a search for token_id=agat_ no longer matches these lines.

If only the directory sync fails after the rename, the change is kept, the request succeeds and a warning is logged. Existing token files readable by group or others are set to 0600 when the store loads; a failure is logged and startup continues.

An opt-in limit of 20 sign-ins per client IP per minute (login_throttle in saml.json, off by default, 429 with Retry-After past that) needs the new client_ip.trusted_proxies list in gateway.json behind a load balancer, or every user shares the balancer's limit.

Such a request is now charged; a request without a body is still not. - **Make the governance audit journal readable by its owner only** — The audit journal holds caller identities, trace ids and delegation and payment details. Its directory is now created owner-only (0700) and its segments, lock file and cursors.json are 0600; they were created with the process umask.

The gateway now uses 0.23.46, which fixes all four.

Requests the gateway cannot parse or recognise, listed in docs/PROTOCOLS.md, are forwarded unrewritten, and a Fabric caller is covered only once its own gateway is upgraded.

The Target must present agent-identity/v1, and when agent identity is configured every credential extension on the card is removed before the gateway adds its own, so a Target cannot assert a DID of its choosing.

- **⭐ Give each Fabric peer and tenant its own share of the shared stream tables** — One peer could fill the capability offer, capability probe or Open replay table and get every other peer refused. Once a table is half full, each peer may hold an eighth of it and the peers of one tenant half, so a second peer is still served after one peer sends hundreds of refused requests, while a single busy peer is not capped while the table has room. The tenant share applies only while other tenants' or untenanted peers hold entries, and the values are fixed. A full capability probe table or share on the sending gateway now answers the caller 429 with Retry-After 5 instead of 502. The listener also admits Opens off its reader loop, at most 16 at a time, holding up to 8 early frames per stream until its Open is admitted or its admission ends, so a slow admission no longer stalls every other message.

A gateway or Connection Point write through this node now ends, at once, only the streams a narrowing change no longer allows. An Open admitted while a revocation runs is refused, and admission reads the Connection Point's current record.

An unknown mediator, one outside the caller's scope and one the gateway may not reference get the same 400, so a scoped caller cannot learn that it exists. An in-scope mediator that is disabled, unregistered or has no usable endpoint gets one generic 400 that names neither the mediator nor its state; the detail is logged server-side. Finalize, recovery and the permanent connection point's listener use only the mediator record validated at accept time, by id: the connection point stores that record id as its `mediator_id`, so another tenant's record with the same DID is not used for it, and deleting the mediator stops its listener. Finalize, like recovery, fails if that record has been deleted, given another DID or disabled since the invitation was accepted. Shared-mediator recovery needs no registered inviter mediator.

- **Refuse tenant and resource-scoped tokens reading user and identity mappings** — GET /v1/users/integrations and /v1/identities/integrations returned the appliance-wide mappings, custom variable values included, to any caller with integrations.view, so a tenant or resource-scoped token could read what it may not change. - **Block tools/call without a readable tool name on every MCP tool gate** — Only Transit Point gating refused a `tools/call` with no `params.name`, or one whose name was not a string. Every other gate checked it as an empty name, which a deny-pattern gate passes, so an upstream that accepted such a call could reach a hidden tool. The direct Access Point, the `fabric://` send leg, the `proxy://` MCP proxy path, Fabric receive and Transit Points now all deny it when tool gating is configured and record a deny decision. Surfaces and Transit Points without gating are unchanged.
- **Refuse MCP POST bodies that are not one JSON object** — A legacy MCP POST whose body the gateway could not parse as JSON, such as a JSON-RPC batch preceded by a UTF-8 byte order mark, was forwarded without tool gating or tool-scoped credential checks, because the gateway found no tool call in it. An upstream with a lenient parser strips the mark and runs every call in the batch, including a tool the gating hides. Access Points, Transit Points, Fabric receive and the standalone MCP Proxy now refuse, before any tool-level control, an MCP POST body that is not one JSON object. They answer with the JSON-RPC errors the Access Point already returned for malformed bodies: `-32700` for a body that is not valid JSON and `-32600` for JSON that is not an object. Other methods cannot carry a body; see "Refuse MCP requests that skip POST admission by method".
- **Refuse MCP POST bodies with duplicate or case-variant keys** — The gateway kept the last of two duplicate JSON keys but forwarded the original body, so an upstream parser that keeps the first could run a different method or tool from the one tool gating and tool-scoped credentials checked. Go's `encoding/json` also matches field names case-insensitively, so `Name` next to `name`, or a lone `Method` or `params.Name`, had the same effect. Access Points, Transit Points, Fabric receive and the standalone MCP Proxy now refuse with JSON-RPC `-32600` an MCP POST body with two keys of one object, at any depth, that are equal or differ only in case. They also refuse a lone case variant of a field the gateway reads: `jsonrpc`, `id`, `method`, `params`, `params._meta`, `params.name` and `params.arguments` of a `tools/call` or `prompts/get`, and `params.uri` of a `resources/read`. Keys inside tool arguments are not case-checked. A legacy request gets HTTP 200 with `id` null. A `2026-07-28` request gets HTTP 400 with the same code, as for any other malformed modern request, and its `id` echoed unless the `id` key itself is duplicated or a case variant.
- **⭐ Require a per-route opt-in before delegated credentials cross Fabric** — A surface with `outbound_credentials` sent the caller's delegated access token to a `fabric://` peer with no separate control: on modern MCP requests through its Target, and on any request through a `fabric://` Transit Point, including A2A requests that carry it as a header. The token now crosses only when that Target or Transit Point sets `fabric_delegated_credentials: true`, and only for that route. With the setting off, the caller's own token is still stripped and the peer gets no delegated credential. The refresh token never crosses Fabric. A Target variant can override the setting, and a `complete` variant that omits it turns it off. A Transit Point that relies only on its own `transit_credentials` is gated the same way.
- **Stop Transit Points from sending another Transit Point's credentials** — On a surface without `outbound_credentials`, a request through one Transit Point picked up the `transit_credentials` of every Transit Point on the surface, so a token meant for one destination could reach another. A Transit Point now uses only its own `transit_credentials`. This also changes `https` Transit Points, which previously received the other Transit Points' tokens too.
- **Stop sending Transit Point credentials to the surface's Target** — On a surface without `outbound_credentials`, a legacy MCP or A2A request through the Access Point injected the `transit_credentials` of every Transit Point into the request to the surface's Target. The Access Point now uses only the surface-level `outbound_credentials`.
- **Send no delegated credential when a Transit Point variant fails to resolve** — A legacy request whose Transit Point variant cannot be resolved still falls back to the base surface, but no longer carries a delegated credential, so a broken variant cannot send the base surface's tokens to a destination the variant did not intend.
- **Apply MCP tool gates that read the caller DID or payment on Fabric routes** — On a fabric:// target, the MCP tool gate's policy input left out the caller's extension identity, and so input.agent.did, and the payment context. A Deny gate whose condition read them switched off, so its tools were listed and callable over Fabric while the same gate blocked them on a direct target, and an Allow gate hid every tool it grants. The input now carries both, as on the direct path.
- **Keep Transit Point credentials on their own upstream after API changes** — After a Transit Point was removed through the API, the next dashboard save gave its credential and its elements to the Transit Point that took its place on the canvas, and saved that Transit Point twice. A credential or a Fabric delegated credentials switch removed through the API also came back from the canvas layout data. The dashboard now matches each Transit Point to its canvas node by its id, does not restore a Transit Point the stored surface no longer has, and takes every stored Transit Point field only from the stored surface.
- **Update quinn-proto to 0.11.19 to fix QUIC denial-of-service advisories** — Bumps the transitive quinn-proto dependency from 0.11.15 to 0.11.19, which fixes five advisories where a remote QUIC peer could exhaust memory (stream reassembly, connection ID retirements, zero-length DATAGRAM frames) or panic the stack (ACK_FREQUENCY minimum ACK delay, zero-length STREAM frames during unordered reads). Restores a passing cargo audit.
- **Update rustls to 0.23.46 to fix TLS advisories** — Bumps rustls from 0.23.45 to 0.23.46, which fixes four advisories where buffered application data could be sent to the outer server after an ECH rejection, Brotli certificate decompression could allocate up to 1 GiB before authentication, an unauthenticated ServerHello could downgrade later connections to classical key exchange, and Debug output of client session values could expose TLS secrets. Restores a passing cargo audit.
- **⭐ Withhold target credentials from callers whose source auth failed** — A caller whose source authentication failed is now forwarded without the stored target credential on `proxy://` MCP Targets, Fabric send, Fabric receive (direct and MCP proxy Targets) and the `a2a-proxy://` Direct Line secret, as the direct inbound path already did. Previously these paths decided from the request path alone or assumed the caller was authenticated, so an anonymous caller on a surface without a denying policy reached the backend with the operator's credential. Agent-card fetches between gateways still carry the receiving gateway's credential.
- **⭐ Refuse tenant token writes to appliance-wide management records** — A tenant access token can still read records that belong to no tenant, but now gets 403 when it updates, deletes or otherwise changes them in JWT verification strategies, secrets, STS clients, mediators, credential providers, certificates, trust authorities, issuers, trust registries, surface templates and integrations (including triggering an appliance-wide integration), and on the appliance Gateway's Connection Points, which tenant tokens can therefore no longer create. Previously these write paths used the read rule, so a tenant could, for example, replace a global JWT strategy's keys. Tenant automations that edited untenanted records need an appliance-wide token, or an operator can assign the record with `PUT /v1/tenant-ownership/...`.
- **Refuse to start when source authentication cannot initialise** — A gateway in Active or Standby mode now exits at startup if the JWT verification strategy store cannot be opened, instead of running with source authentication silently disabled and attaching target credentials for every caller. A Fabric message that reaches a surface with caller authentication before source authentication is ready, or a direct request on a surface whose source authentication is missing, now gets 500. A fresh install is unaffected, because the store directory is created on first start.
- **Stop logging integration credentials and webhook URLs** — The integration test endpoint no longer logs the submitted configuration or content, and Slack, webhook and Redis Streams publishers no longer log webhook URLs, Redis connection strings or URLs inside HTTP errors, which can carry passwords and bearer tokens.
- **Accept one connection setup per gateway invitation, and only that one** — A gateway invitation now accepts a connection setup only on a User Connection Point with a secret, only when the setup's parent thread id names the invitation message the mediator served, and only once. Previously the parent thread id was ignored, a leaked invitation URL and secret could be redeemed repeatedly until it expired, and system Connection Points with an empty secret accepted setups, each one creating an approval request, an admin notification and integration calls. The secret is now compared in constant time, and a setup that fails after its secret is accepted, such as at the appliance gateway limit, leaves the invitation unused so the peer can retry.
- **Answer 404 for records a tenant token cannot see on every write** — Updating, deleting or otherwise changing another tenant's record now returns the same 404, with the same body, as a missing record across all management stores, Gateways, Connection Points, Agent Surfaces, policies and API keys, so a tenant token cannot tell that an id exists in another tenant. Secrets, certificates and API keys outside the token's resource pattern answer the same way. A record the token can see but not change, such as an appliance-wide one, still returns 403. Previously these writes returned 403 for another tenant's record.
- **Publish the Docker Compose ports on loopback only** — docker-compose.yml now publishes the HTTPS (8443) and HTTP (8080) listeners on 127.0.0.1 instead of every host interface, so a local gateway is not reachable from the network before its first administrator registers. Remove the 127.0.0.1 prefix to expose it deliberately.
- **Cap Legacy SSE sessions at 10,000 and answer further GET /sse with 429** — GET /sse on proxy:// and fabric:// surfaces and on standalone MCP proxies created a session with no limit, so a client could open sessions until memory ran out. The gateway now holds at most 10,000 Legacy SSE sessions, matching the Streamable HTTP notification stream cap; sessions whose client has disconnected are dropped first, and a request beyond the cap gets 429 "Too many active SSE sessions".
- **⭐ Verify x402 payments against the surface's configured requirements** — x402 verification now requires a credential's `accepted` object to name one of the payment requirements the surface issued, exactly in scheme, network, asset, recipient, amount, asset transfer method and EIP-712 domain, and rejects it in every verification mode otherwise. Signature, on-chain and facilitator checks take their expected values from that requirement, embedded and external facilitators receive it as `paymentRequirements`, and the transaction record and settlement use it. Previously a credential was checked only against its own `accepted` object. Deferred settlement records written by earlier builds settle only if they still name one of the surface's current requirements, and are marked failed otherwise.
- **Enforce access-token scopes on the JWT verification strategy routes** — The /api/v1/jwt-verification-strategies routes (list, get, create, update, delete and validate-jwks-uri) now also require the matching jwt_verification_strategies feature in a scoped personal access token's scopes, instead of checking only the owner's role. Session logins and tokens without feature scopes are unchanged.

### Changed

- **Skip the token lock for access token uses inside the usage write interval** — A use of an access token within 60 seconds of its last recorded use no longer waits on the token's lock, so concurrent requests with the same token do not queue behind a file write. The 60 second check is repeated under the lock before writing.
- **Document access token rotation refusal behavior** — The access token and observability guides now explain that callers receive 403 when they do not control a token, including unknown ids, and that authentication middleware refusals do not emit rotate_denied events.
- **Send no-store on access token create and rotate responses** — Responses that return a token secret now carry Cache-Control no-store so caches never keep them.
- **Document access token rotation behavior** — Updates the access token reference with the rotation endpoint and its authorization, lifecycle, and audit behavior.
- **Document browser sign-in for the fabric CLI** — Documents the browser sign-in flow, consent step, PKCE exchange, and safe redirect behavior in the capabilities, access token, and architecture guides.
- **Check the A2A request shape against the A2A version of its method** — With full validation (Envelope + A2A fields), the spelling of the method now picks the rules: message/send is checked against what A2A 0.3 defines (role user or agent, parts of text, file or data, kind when present) and SendMessage against what A2A 1.0 defines (role ROLE_USER or ROLE_AGENT, parts of text, raw, url or data), and the task-listing status filter likewise. A value the method's version does not allow, such as role user on SendMessage, is refused with -32602, naming the field; before, either version's values passed on any method. Fields a version does not define, such as kind on a 1.0 request, are ignored, as A2A 1.0 says implementations should. The negotiated A2A-Version is not consulted.
- **⭐ Start new A2A proxy surfaces at A2A 1.0 only** — An A2A proxy surface accepts fixed A2A versions, and its generated agent card lists them. A new one, or one whose Target moves to an A2A proxy, accepts 1.0 only, so its callers send A2A-Version 1.0. A surface stored before this release is given its versions when it is loaded, 0.3 and 1.0 (1.0 only if the retired a2a_legacy_compatibility flag was off), so its callers, including those that send no A2A-Version header, keep working unchanged, provided they send a well-formed JSON-RPC request: an A2A proxy Target always checks the JSON-RPC envelope, even where [a2a] validate_messages is false, and a startup warning names those surfaces. The surface API refuses a change to an A2A proxy surface's versions; a block that names no versions takes the fixed ones, and a warning is logged when moving a Target to an A2A proxy narrows a surface's versions.
- **List both A2A versions on the onboarding agent card** — The onboarding agent card belongs to no surface, so it now always lists A2A 0.3 and 1.0 and carries the v0.3 fields. It no longer follows the retired a2a_legacy_compatibility flag. What the onboarding agent serves is unchanged.
- **Apply A2A version negotiation and validation to fabric:// surfaces** — An A2A surface whose Target is fabric:// now applies its accepted versions and validation level on the sending gateway, before the request is paid for or sent over the fabric, as a surface with a managed-agent Target does. Previously these checks were skipped, so the A2A Protocol settings saved on such a surface had no effect. With the default settings, only unsupported A2A versions and requests that are not a single, well-formed JSON-RPC request are newly refused, which a conformant agent refuses too. A fabric surface given settings on upgrade where the retired a2a_legacy_compatibility flag was off accepts A2A 1.0 only, as other surfaces already did. The receiving gateway does not run the checks again, and the version metric counts fabric traffic on the sending gateway.
- **Deprecate [a2a] validate_messages in favour of per-surface validation levels** — Validation is now set per A2A surface: off, envelope (valid JSON, jsonrpc 2.0 and a string method, which refuses batches) or full (also the A2A request shape). When surfaces are loaded, one stored without its own settings takes envelope, or off when [a2a] validate_messages is false; it never takes full. A startup warning asks for the key to be removed, and it is removed from the example configuration. With the DynamoDB configuration source the retired switches are not applied, and the startup warning says so. - **Reject an access token secret rotated while its request was being authenticated** — A request that presented a token's old secret and was still being authenticated when a rotation replaced that secret is now refused with 401, instead of being let through once. A token revoked or expired in that window is refused the same way.
- **Document which storage paths resolve from the working directory** — CONFIGURATION_REFERENCE.md said every storage path resolves from the folder holding config.toml. It now names the keys that resolve from the working directory or from --base-folder, and points deployments to absolute paths.
- **Answer A2A proxy SendMessage requests with A2A 1.0 replies** — The A2A proxy answered every request in the A2A 0.3 shape, which A2A 1.0 clients cannot read. It now picks the shape from the send method: SendMessage gets the 1.0 SendMessageResponse (result.message, role ROLE_AGENT, parts without kind), and message/send keeps the 0.3 reply (the message itself, kind message, role agent), whatever A2A-Version the caller sends.
- **Audit requests denied because a policy could not decide** — When a gateway, access-point inbound, surface or MCP tool policy raised an evaluation error, had no policy engine, or was enabled without a compiled policy, the request was denied without a policy decision record. These denials are now recorded with decision error and deny_reason evaluation_error, no_policy_manager or policy_not_compiled, on the direct, Fabric and MCP-proxy paths.
- **Audit trust checks that failed on an unavailable A2A proxy agent card** — When an A2A proxy target's agent card could not be synthesized, its target-leg trust checks failed with AGENT_CARD_UNAVAILABLE without a trust_check audit record or metric. They are now recorded like the same failure on the outbound path.
- **Keep delegation audit records when a request ends before its VP is minted** — Credential delegation records held back until the request's identity VP was minted were lost when the request returned early, for example with 503 when delegated credentials were unavailable. They are now recorded without a VP on every path.
- **Send Retry-After when an Access Point rate limit refuses a request** — A request refused with 429 by an Access Point rate limit now carries a Retry-After header; it was never set.
- **Keep the audit pipeline running when its journal or cursors are damaged** — An unreadable line at the end of the audit journal, or an unreadable cursors.json, stopped the audit pipeline from starting, so the gateway kept serving with no audit records kept or forwarded until restarted with the file repaired. An unreadable line elsewhere in the journal stopped every sink behind it for good. On start the journal is now cut back to its last readable line and an unreadable cursors.json is renamed to cursors.json.corrupt-<unix seconds>; readers move past unreadable lines and count them in agent_gateway_audit_sink_skipped_total with reason corrupt. agent_gateway_audit_pipeline_started reports 0 when the pipeline could not start.
- **Pause a disabled Governance Audit integration without replaying old records** — Records addressed to a Governance Audit integration that was disabled, given a tenant or moved to another category were passed over as delivered until its delivery stopped, and its undelivered records could later be deleted uncounted or replayed when it was re-enabled. A paused or deleted Governance Audit integration now receives nothing. Its undelivered records are let go and counted in agent_gateway_audit_sink_skipped_total with reason paused, with one warning per integration, and a deleted integration's position is dropped. Resuming continues from the pause, so only records produced after it are delivered. Until delivery stops, each record it refuses is counted in agent_gateway_audit_forward_total with result not_receiving rather than reported as delivered. Records produced at the moment of pausing may still be delivered after it resumes, or be counted as paused.
- **Record x402 settlements that fail immediately** — An immediate x402 settlement that returned an error without marking itself failed left the transaction without a settlement failure. It is now marked failed and recorded once as a failed payment event.
- **Run the governance audit pipeline only on the Active node** — A Standby node also started the audit pipeline, so in a failover pair sharing storage both nodes could open the same journal, write records with the same sequence numbers and overwrite each other's cursors, and a promoted node continued from a stale position. Only the Active node now runs the pipeline. Stepping down journals what was handed over, stops delivery and releases the journal; becoming Active re-opens the journal and cursors from disk and continues after the last record. The journal holds an exclusive lock, so a second writer cannot open it, and a node that becomes Active while another still holds it tries again every 5 s. agent_gateway_audit_pipeline_started is 0 on a Standby node.
- **Retry rebuilding the audit sinks when integrations cannot be listed** — When the integrations could not be listed, the previous audit sinks were kept until the next settings or integration change, so a just-disabled integration could keep receiving records. The rebuild is now retried every 5 s until it succeeds and each failure is counted in agent_gateway_audit_sink_rebuild_failed_total. Rebuilds also run one at a time, so a slower rebuild can no longer replace newer sinks. A rebuild before integration storage is set up counts as a failed listing rather than as no integrations.
- **Re-read the audit journal after a failed append that could not be undone** — When appending to the audit journal failed and the partial batch could not be cut off again, the next batch was written after the partial line. The segment is now re-read before the next append, as on start, so no partial line is left behind and no sequence number is reused.
- **Build the audit sinks before the audit pipeline starts** — The audit pipeline started before the Governance Audit integrations were loaded, and a node becoming Active kept the sinks it had built before, missing integration changes made on the other node. The sinks are now built from the current settings and integrations every time the pipeline starts, on start-up and on becoming Active; while the integrations cannot be listed the pipeline waits and tries again every 5 s.
- **Stop every audit pipeline job when a node steps down** — A node stepping down waited for the audit journal writer, which kept retrying a failing journal, then aborted the dispatcher while its readers kept delivering and saving cursors on their own. Stepping down now gives the writer up to 5 s to journal what it was handed, then cancels the writer, the dispatcher and every reader, dropping any delivery in flight; records still unwritten are counted in agent_gateway_audit_records_lost_total with reason aborted. No cursor is saved afterwards, and the journal lock is released only once every job has stopped. Waiting to take over the journal and retrying a failed sink rebuild also end on stepping down. A writer stuck inside a disk write keeps the lock and an error is logged; the node must then be rebooted.

- **Show integrations that can no longer be attached so they can be removed** — A stored mapping whose integration was deleted, re-categorised or given a tenant was invisible on the integration pages but still sent on save, so the user and identity pages could not be saved once the API began refusing such mappings. These now show as NOT AVAILABLE rows with a Remove button and block Save until removed, and the selector offers only integrations the page can attach.
- **⭐ Attach an integration to events as soon as it is selected** — Choosing an integration on the gateway, connection point, user and identity integration pages did nothing, so Save stayed disabled and no events could be wired up. Selecting one now attaches it with its template's custom variables, opens it to choose events, and removes it from the selector.
- **Show load and save failures on user and identity integration pages** — Both pages reported a failed save as success and showed a failed load as an empty list that could then be saved over the stored mappings. Failures now show the server's message, and a failed load offers no editor.
- **Require an event for each integration on user and identity pages** — Save stays disabled until every attached integration names at least one event, matching the API, and missing custom variables are checked against the integration's template.
- **Give the fabric tools/list gate the caller identity it decides on** — An MCP tool gate whose condition reads the caller - anything under input.source_auth - could never match when tools/list was answered over the fabric leg: that filter built its policy input without the caller's source authentication, so the condition was unknowable. An unknowable condition forces an Allow gate inactive, so under a deny-by-default gating config every tool the gate would have granted was hidden, with no error and an empty tool list. The filter now carries source_auth and identity_binding and normalizes the caller DID, exactly as the tools/call gate on the same leg already did, so a tool shown in the list is the one the call gate admits.
- **Fix storage backups failing restore with duplicate manifest entries** — Backups taken from storage that contained a legacy backup manifest file under META-INF carried two manifests and failed to restore with "backup contains duplicate manifest entries". Restoring a backup whose manifest uses the legacy name could leave that file in storage. Backups now skip stray manifest files and log that they can be deleted, restores never write either manifest name into storage (including dot-segment variants of the name), and an archive carrying both manifests is validated against the current one, so backups already taken this way restore again.
- **Keep the canvas Entry point URL copy button visible and clickable** — With a long URL on a canvas that was not wide enough, the URL banner at the top of the Surface Builder slid under the canvas toolbar, so its copy button sat beneath the disabled Undo button and could not be clicked, or was pushed out of the banner. The variants widget, the banner and the toolbar now share one row along the top of the canvas, so the banner shrinks to the space between them and only its URL text is truncated. Copying uses the shared copy button, and a refused copy, for example on a plain-HTTP origin, now shows an error toast instead of failing silently.
- **Apply tool-scoped credential bindings only to tools/call on Access Points** — An Access Point matched `required_for.tools` against `params.name` of any legacy MCP method, so a `prompts/get` whose name equalled a listed tool picked up the tool-scoped credential. Only a `tools/call` now names a called tool; the `input.mcp.tool_name` policy input is unchanged.
- **Apply tool-scoped credential bindings on Fabric receive** — Fabric receive passed no tool name to credential delegation, so a binding with `required_for.tools` on the receiving surface never applied. It now matches `params.name` of a `tools/call`, read after admission has refused batches and ambiguous keys, because Fabric receive forwards only to its own Target. Upgrade note: such a binding now sends the delegated credential to that Target for the listed tools, or asks for consent when no credential is stored.
- **Keep Transit Points with credentials when saving a reloaded surface** — After a surface was reloaded in the dashboard, saving it from any panel other than its Transit Point's dropped the whole transit block when a Transit Point had credentials, so the gateway lost its Transit Points while the canvas still showed them. The Surface Builder now accepts the credentials in the shape they are loaded in, so every Transit Point on the canvas is saved. It also keeps a stored elicitation timeout and fallback, which a save used to reset to 300 seconds and on_demand.
- **Keep explicit empty or zero retry values when saving from the dashboard** — Saving a surface from the dashboard dropped an empty list of retryable status codes, so the gateway fell back to its default codes and retried calls on 5xx that the operator had limited to connection errors. Zeros for retry attempts, the circuit-breaker failure threshold and its timeout were saved as 3, 5 and 30. The dashboard now keeps these values as stored. An empty list shows as a new Retry on connection errors only switch, an empty codes field still means the gateway default, and input that is not a list of HTTP status codes blocks Save instead of being saved as an empty list.
- **Stop the dashboard restoring Networking settings removed through the API** — After Networking was changed or removed through the API, the next dashboard save could write the old settings back from the canvas layout data, or write a Transit Point's settings to the Target and the other way round when the API moved Networking between them. The dashboard now takes Networking settings only from the stored surface, for the Target and for each Transit Point.
- **Run the MCP conformance harness on Node 22** — The pinned @modelcontextprotocol/conformance suite imports fs.globSync, which only exists in Node 22 and newer, so every conformance scenario crashed on load in CI under Node 20. The CI conformance job now uses Node 22, and the harness preflight, package engines and docs require Node 22 or newer instead of 20.18.1.
- **End only the MCP subscriptions on the changed surface or tenant** — Saving or deleting one surface, or changing its surface policy, now ends only the open MCP subscriptions on that surface, and changes to a tenant's MCP proxies, JWT verification strategies or credential providers end only that tenant's subscriptions. Previously any of these ended every open subscription on the gateway, so one tenant's configuration writes disconnected every other tenant's subscribers. Gateway and global policy changes, API-key changes, delegation vault revocation, JWT strategy reload, policy updates on surfaces with a response policy (whose engine is shared by definition) and changes to appliance-global or re-owned resources still end every subscription. A subscription that falls more than 1024 changes behind ends on the next change.
- **Show one save button and an honest value reveal in the secret editor** — The secret editor had two save buttons and a reveal toggle that showed an empty field, because stored secret values are never returned by the API. The editor now has a single save button, marks the stored value as hidden, and offers the reveal toggle only for a value entered or generated on the page. Cancelling a value update or saving it clears the entered value from the page, and Save is enabled only when something has changed, so undoing an edit no longer sends an empty update.
- **Refuse secret updates and deletes when the secret cannot be loaded** — Updating or deleting a secret now returns 404 when it does not exist and 500 when it cannot be read, before any write. Previously the ownership check was skipped when the lookup failed, and a missing secret returned 400.
- **Read each vault's consent epoch once per second for all its subscriptions** — MCP subscriptions on the same delegation vault now share one consent-epoch watcher instead of each re-reading the epoch every second, so vault reads (and kms:Decrypt calls with the aws_kms backend) no longer grow with the number of open subscriptions. A changed epoch ends the subscriptions started under an earlier one. A subscription whose epoch differs from the watcher's last reading reads the epoch once more before joining, so one started under a newer epoch, or after the vault recovers, is not closed by a stale reading. The watcher stops when the last subscription on the vault closes.
- **Sign the release PR commit created by the Prepare release workflow** — Prepare release committed with git on the runner and pushed, so the release PR commit was unsigned and could not be merged into main, which requires signed commits. It now creates the commit through the GraphQL createCommitOnBranch API with the release App token, so GitHub signs it and it shows as Verified. The release PR is titled chore(release): prepare vX.Y.Z so its squash merge passes the conventional commit message rule, and RELEASING.md explains that wording edits must be signed or made in the web editor.
- **Count MCP SSE streams as active connections until they end** — Legacy MCP SSE passthrough responses, legacy GET /sse streams on proxy:// and fabric:// surfaces, and the Streamable HTTP GET notification stream now hold their connection guard until the response body ends or the client disconnects, as modern MCP streams already did. Before, the guard was released when the response headers were sent, so running streams were missing from the active-connection metrics.
- **Keep idle long-lived streams in the active-connection count** — The task monitor no longer resets a task's active connections to zero after two minutes without activity. Every request's connection guard releases its count when the request or stream ends, so the reset only hid quiet streams and listens from the dashboard, Prometheus, CloudWatch and OpenTelemetry active-connection gauges.
- **Drop connections and streamed responses without panicking outside the runtime** — Dropping a connection guard, or any streamed MCP response body (legacy or modern), outside a Tokio runtime, for example during shutdown, no longer panics. A modern response's completion bookkeeping (connection count, bytes, errors, metrics) is skipped with a warning instead of spawning a task, and a guard leaves its count as is. Releasing a guard when its stream ends no longer logs the abnormal disconnect warning.
- **Show the Networking settings of a surface configured through the API** — The surface builder's Networking element converted its panel settings to the stored shape on save but could not read the stored shape back, so a surface whose `target.networking` was set through the API (or by another tool) showed Networking as unconfigured with empty fields, although the timeouts, retries and circuit breaker were in force. The element now reads the stored timeout, retry (including retryable status codes), circuit breaker and mirror settings into the panel, on the surface and on each transit point. Settings that are not stored stay off; no defaults are filled in.
- **Keep a surface's Target Networking settings when saving it after a reload** — After a surface was reloaded in the dashboard, its Target Networking element sat ahead of the Target on the canvas, and saving the surface left out `target.networking`, so the timeouts, retries, circuit breaker and mirror stopped applying. This happened whether Networking was set in the dashboard or through the API. The element is now saved wherever it sits on the Access Point to Target edge.
- **Limit /api/v1/permissions for access tokens to the token's own scopes** — A personal access token now sees only the features its scopes grant, capped by its owner's role, instead of the full role. The response is also sent with no-store and Vary Authorization, Cookie so it is not cached across credentials.

### Removed

- **Remove the global A2A legacy compatibility flag in favour of surface settings** — The a2a_legacy_compatibility Settings flag is replaced by each A2A surface's accepted versions. When surfaces are loaded, an A2A surface stored without its own settings is given them from the previous gateway-wide switches and they are written to storage: A2A 1.0 only if the flag was off, both versions otherwise. Versions before this change cannot read a surface with access_point.a2a, so rolling back needs the block removed from each stored surface first.
- **Remove the unused Pre-Authorize Blocked governance audit event** — The audit.pre_authorize_blocked event type is no longer offered for Governance Audit integrations, and the Audit page no longer has a label for it. Nothing in the gateway ever recorded this event, so no audit records are affected.
- **Remove the unused version-bump check script** — scripts/check-version-bumps.sh was never wired into any workflow and described the old tag-per-PR release model, which the Prepare/Publish release workflows replace.
