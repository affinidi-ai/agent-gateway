## [Unreleased]

## [1.0.0] - 2026-10-19

### Breaking

- **⭐ Record only the audit events each destination selects** — The VP Audit Log and each Governance Audit integration now record only the audit events selected for them, and nothing is selected by default. After upgrade, the VP Audit Log keeps policy decisions, trust checks and VP injections only if they were enabled before; credential delegation, payment and trace-termination records, which were always written, stop until selected in Settings › VP Audit. Existing Governance Audit integrations receive nothing until events are listed in their audit_events.
- **Deliver governance audit records at least once from a durable journal** — Audit records are journalled to disk before any destination receives them, and each destination reads the journal from its own position, so a slow or unreachable integration falls behind instead of losing records, and delivery resumes after a restart. A record may be delivered more than once; deduplicate on event_id. Integrations no longer depend on the VP Audit Log keeping a record. The journal lives in the audit log directory under journal/, and a crash loses at most the last batch not yet synced to disk. While the journal cannot be written up to 10,000 records wait in memory; beyond that the oldest are discarded and counted in agent_gateway_audit_records_lost_total with reason journal_write. The journal size is reported in agent_gateway_audit_journal_bytes and logged as a warning above 256 MiB; above 1 GiB the destinations still holding back its oldest part are moved past it, and what each skips is counted in agent_gateway_audit_sink_skipped_total with reason backlog_cap. The VP Audit Log never writes the same record twice. A record no destination selects is not built at all, so unselected events cost nothing, including the signed VP a consent-granted record may carry.
- **Store VP Audit selections as audit_events instead of audit_categories** — The settings API takes and returns audit_events, a list of event names such as policy_decision, and rejects names that are not audit events. A request that still sends audit_categories gets 200 and the field is ignored; send audit_events instead. Settings stored with audit_categories are read as the matching events (policies as policy_decision, trust_checks as trust_check, identity as vp_injected), so existing selections are kept.
- **Remove the dropped result from agent_gateway_audit_forward_total** — Records are no longer dropped from a full forwarding queue, so agent_gateway_audit_forward_total no longer reports result dropped, and integration_id is never empty. Alert rules on result dropped never fire; alert on agent_gateway_audit_sink_skipped_total and agent_gateway_audit_records_lost_total instead.
- **Answer full Fabric stream caps on the receiving gateway with capacity_reached** — A full framed-stream cap, Open replay table or table share, a full admission pool, or a peer past its Open rate, is now refused with capacity_reached instead of unavailable, so the sending gateway's caller gets 429 with Retry-After instead of 502. A 1.0.0 sender cannot parse capacity_reached, so while a pair runs mixed versions its callers wait for their response deadline, holding its stream slots, whenever the upgraded receiver is out of room. Normal traffic is unaffected. Upgrade both gateways of a pair together, or the sending gateway first, as an upgraded sender understands both codes.
- **⭐ Refuse did:web and did:webvh on private hosts unless allow_private_hosts is on** — DID resolution now refuses a host that is, or resolves to, a loopback, private-network, carrier-grade NAT or link-local address, and does not follow redirects; each method also refuses some local names outright. This closes an SSRF path through attacker-supplied DIDs and applies to every resolver the gateway builds. A stored mediator document is served from cache only until the resolver's TTL expires, so a stack whose mediator or peer DIDs live on such hosts must set the startup-only `[did_cache] allow_private_hosts = true`, which logs a warning at startup and also reopens cloud metadata. `scripts/_prepare.sh` turns it on for local and Docker dev stacks, and the BDD configs turn it on too.
- **⭐ Newly paired Remote gateways reach no surface until one is exposed** — Every pairing path, including the inbound handshake, now creates the peer with exposure mode `none`, so it can neither forward to nor list any local surface until an operator exposes one. An exposure update without `exposure_mode` and with an empty list now means `none`, not every surface. The capability query now filters on the authenticated sender's exposure and returns nothing when that lookup fails, instead of every surface.
- **⭐ Never apply tool-scoped credential bindings on Transit Points** — A legacy MCP request through a Transit Point matched `required_for.tools` against the JSON-RPC method, so a binding that listed a tool never applied there, while one that listed a method such as `tools/call` or `message/send` did. A `2026-07-28` `tools/call` matched on the tool name. Transit Points now apply only `all` bindings. Bindings carry no destination, and a partner upstream names its own tools, so a tool name that collided with one of the Target's tools would hand the partner a credential meant for the Target. `all` bindings still reach every Transit Point of the surface, including the `transit_credentials` that a surface without `outbound_credentials` reads as `all`. Access Points are unchanged. Upgrade note: a binding that lists a JSON-RPC method, or a tool called through a Transit Point with `2026-07-28`, no longer sends its credential to the Transit upstream. Use an `all` binding only if every Transit Point's upstream should receive it.
- **Refuse MCP requests that skip POST admission by method** — MCP admission, including the batch and single-object checks, ran only for POST. A PUT or PATCH, or a GET or DELETE with a body, reached the upstream without them, so an upstream that routes by path whatever the method could run a batch or a gated tool. Access Points, Transit Points and Fabric receive now answer 405 with `Allow: POST, GET, DELETE, HEAD, OPTIONS` to any method but those five, and 400 with JSON-RPC `-32600` to any non-POST request with a body. A standalone MCP Proxy answers DELETE with 405 and `Allow: POST, GET, HEAD`. GET and DELETE without a body behave as before. Upgrade note: an MCP client that sends PUT, PATCH or a body on GET or DELETE is now refused, as is an MCP POST whose body is not valid JSON or is JSON but not an object, on Access Points, Transit Points, Fabric receive and the standalone MCP Proxy.
- **Stop sending delegated credentials over Fabric unless the route opts in** — After upgrade, `fabric://` Targets and Transit Points on surfaces with `outbound_credentials` stop sending delegated access tokens to the peer, because the new `fabric_delegated_credentials` setting defaults to off and no migration turns it on. Turn the setting on for each Target or Transit Point whose peer relies on receiving the token, including `fabric://` Transit Points that rely only on their own `transit_credentials`. This includes A2A surfaces whose `fabric://` Transit Points sent the token as a header; A2A Access Point traffic over Fabric never carried it and is unchanged. Transit Points on surfaces without `outbound_credentials` also stop receiving other Transit Points' `transit_credentials`; give each one its own binding if it needs a token. The surface's Target on such a surface also stops receiving Transit Points' `transit_credentials`; add the binding to `outbound_credentials` if the Target needs it.
- **Apply mcp_http Origin and size limits to every MCP endpoint** — `mcp_http` Origin allowlist, header budget and `max_request_bytes` (default 1 MiB) now apply to every MCP endpoint and to `2024-11-05` traffic as well, so legacy browser clients whose Origin is not allowed get `403`, and oversized requests get `413`/`431`. Before upgrading, add browser origins to `mcp_http.allowed_origins` and raise `max_request_bytes` / `max_header_bytes` on endpoints that need them. Public endpoints given as bare listen addresses are skipped by the Origin check; any other public endpoint that is not an HTTP(S) origin is skipped with a warning.
- **⭐ Admit MCP 2026-07-28 on every MCP endpoint and retire mcp_protocol_mode** — Access Points, Transit Points, MCP Proxies and Fabric framed streams now admit MCP `2026-07-28` alongside `2024-11-05` without configuration, instead of rejecting it with `400` / `-32022` unless the endpoint was set to `dual`. `mcp_protocol_mode` is retired: stored records and API payloads that carry it still load, the value is ignored, it is dropped on the next save and no longer returned. There is no per-endpoint opt-out, so a modern request to a legacy-only upstream gets `502`. Buffered Fabric `ForwardRequest` stays `2024-11-05`-only.
- **Stop sending target credentials for failed callers over MCP proxy and Fabric** — Backends behind `proxy://` MCP, `a2a-proxy://` or Fabric surfaces with source authentication now receive requests from failed callers without the target credential, and will usually reject them. Two Fabric gateways that both require source authentication on the same header now reach the backend without the target credential, because the sending gateway strips that header; require caller authentication on one side of the hop or use a different header on each side (see docs/POLICY.md).
- **Refuse tenant token edits to records that belong to no tenant** — Tenant automations that updated, deleted or triggered appliance-wide records, including records created before tenant stamping, now get 403, and tenant tokens can no longer create Connection Points. Use an appliance-wide token, or have an operator assign the record with `PUT /v1/tenant-ownership/...`.
- **Pair one gateway per invitation and recreate invitations made before upgrade** — Each gateway invitation now pairs a single gateway; create a new invitation for every peer, including after rejecting a request. Invitations created before this release recorded a different invitation message id and are refused, so create them again.
- **Stop starting when the JWT verification strategy store cannot be opened** — A gateway in Active or Standby mode now exits at startup if its JWT verification strategy store cannot be opened, even when no surface uses caller authentication. Before upgrading, check that the gateway user can create and read the `jwt_verification_strategies` directory next to the secrets storage directory.
- **Publish Docker Compose ports on 127.0.0.1 instead of every interface** — A gateway started with docker-compose.yml is no longer reachable from other hosts on ports 8443 and 8080. Remove the 127.0.0.1 prefix in docker-compose.yml to expose it deliberately.
- **Require the payment requirement in fabric x402 verify-requests** — In `fabric_gateway` verification mode the requesting gateway sends its resolved requirement as `payment_requirement`, and the facilitator gateway verifies against it and rejects a verify-request without one. Upgrade requesting gateways first; an upgraded facilitator rejects every verify-request from a requester on an earlier build.
- **Accept no x402 payment on a surface without payment requirements** — A surface with x402 enabled and an empty `payment_requirements` list, or a requirement whose `amount` is not a number (such as one created from the x402 Payment Wall template before an amount is set), rejects every payment.
- **Take x402 signature-check fields from the configured requirement** — Clients no longer supply the transfer method or EIP-712 domain. For signature checks, an `eip3009` requirement needs `extra.assetTransferMethod`, `extra.name` and `extra.version`, and a `permit2` requirement needs `extra.assetTransferMethod`. A client must echo the issued requirement, including those fields, and an `upto` payment must authorise exactly the configured amount, as must every signed authorization.
- **Refuse SPL token requirements on Solana transaction-hash verification** — Solana transaction-hash verification checks native SOL lamports only, so a requirement for an SPL token is refused there and must use the `spl_transfer` method. A transaction that is not JSON-encoded is refused rather than checked without its recipient.
- **Require token_name and token_version for the EIP-3009 x402 test endpoint** — The x402 test endpoints issue and verify one requirement built from test-endpoints.json. `/protected` (EIP-3009) needs the new optional `token_name` and `token_version` fields in the `evm` entry, since the EIP-712 domain is no longer taken from the client.

### Security

- **Escape the token id from the request path in access token log events** — The token id taken from the request path on access token update, revoke and rotate log events, including access_token.rotated and access_token.rotate_denied on the audit target, is now logged as an escaped string, so a newline in the path cannot start a forged line in the plain log format. In the plain log format the value is now double-quoted, for example token_id="agat_...", so a search for token_id=agat_ no longer matches these lines.
- **Write access token files atomically with owner-only permissions** — Token files are written to a temporary file with mode 0600, renamed into place and the directory synced, so they are never readable by other users or left half written. If only the directory sync fails after the rename, the change is kept, the request succeeds and a warning is logged. Existing token files readable by group or others are set to 0600 when the store loads; a failure is logged and startup continues.
- **Stop returning storage error details from access token endpoints** — Create, update and revoke no longer include the underlying IO error text in 500 responses; the error is logged instead.
- **Bound outstanding SAML sign-ins** — The gateway tracks at most 100,000 unfinished SAML sign-ins and answers 503 on /api/saml/login past that, instead of holding them without limit. An opt-in limit of 20 sign-ins per client IP per minute (login_throttle in saml.json, off by default, 429 with Retry-After past that) needs the new client_ip.trusted_proxies list in gateway.json behind a load balancer, or every user shares the balancer's limit.
- **Deny Fabric requests to a surface with OPA enabled but no compiled policy** — A Fabric request to a surface that has OPA enabled but no compiled policy is now denied, as the direct path already did; it was let through. Request-path tests of the Fabric surface-policy gate cover it.
- **Enforce the appliance-wide surface policy on every Fabric request** — The appliance-wide surface policy now runs on every Fabric request; it ran only when the surface had its own compiled policy. Request-path tests of the Fabric surface-policy gate cover it.
- **Stop returning OPA engine error text to callers** — When a policy cannot decide, callers get the generic denial and the OPA engine's error detail stays in the gateway log; the error text was returned to the caller.
- **Make the governance audit journal readable by its owner only** — The audit journal holds caller identities, trace ids and delegation and payment details. Its directory is now created owner-only (0700) and its segments, lock file and cursors.json are 0600; they were created with the process umask.
- **Update rustls to 0.23.46** — rustls 0.23.45 had four advisories, RUSTSEC-2026-0346 (Debug output of client session values exposed TLS secrets), RUSTSEC-2026-0347 (buffered data sent to the outer server after an ECH rejection), RUSTSEC-2026-0348 (Brotli certificate decompression could allocate up to 1 GiB before authentication) and RUSTSEC-2026-0349 (an unauthenticated ServerHello could downgrade later connections to classical key exchange). The gateway now uses 0.23.46, which fixes all four.
- **Rewrite Target endpoint URLs in extended agent cards** — Extended agent cards on A2A and AP2 surfaces, returned by GetExtendedAgentCard and agent/getAuthenticatedExtendedCard or fetched from extendedAgentCard (1.0, including tenant-scoped paths) or v1/card (0.3), now have their endpoint URLs rewritten to the gateway on inbound, fabric and outbound paths and get the same agent identity treatment as the public card, so callers no longer learn the Target address from requests the gateway recognises. The HTTP+JSON path is resolved against the Target's base path both as the forwarded URL is and as lenient Target routers do, and a path that climbs out of the base or above the root (which covers fabric targets, whose peer base path is unknown) or cannot be parsed is treated as a card. An extended-card response the gateway cannot rewrite, including one with no endpoint field, is answered with 502 (a JSON-RPC -32603 error echoing the request id on the JSON-RPC binding), and an extended-card request inside a JSON-RPC batch is rejected with -32600. Requests the gateway cannot parse or recognise, listed in docs/PROTOCOLS.md, are forwarded unrewritten, and a Fabric caller is covered only once its own gateway is upgraded.
- **Never trust an identity credential already on an extended agent card** — An agent-identity-credential/v1 extension already on an extended card no longer stands in for the agent identity, directly or over Fabric, because a peer gateway never issues one there. The Target must present agent-identity/v1, and when agent identity is configured every credential extension on the card is removed before the gateway adds its own, so a Target cannot assert a DID of its choosing.
- **Pin GitHub Actions and reusable workflows** — Pin CI dependencies to immutable commits and scope checks to read-only repository access.
- **Verify release PRs before publishing and protect release tokens** — Publishing now verifies that the triggering commit belongs to a release pull request, disables persisted checkout credentials, and uses explicit token headers for release pushes.
- **Require protected release environment configuration** — Document that release secrets require a protected main-only environment, required reviewers, and a dedicated least-privilege GitHub App.
- **Reject invisible Unicode format characters in display names** — Display names and descriptions now reject Unicode format (Cf) characters such as zero-width spaces, bidirectional overrides and tag characters, as well as control characters. Names read from remote Agent Cards, signed into VCs or published to trust registries can no longer visually impersonate another agent's name.
- **Escape variable values in Slack messages so they cannot mention or link** — Slack integrations now escape &, < and > in substituted variable values. Caller-supplied text, such as a JWT name or a registration username, can no longer render as a channel-wide mention or a disguised link. Admin-written templates are unchanged.
- **⭐ Give each Fabric peer and tenant its own share of the shared stream tables** — One peer could fill the capability offer, capability probe or Open replay table and get every other peer refused. Once a table is half full, each peer may hold an eighth of it and the peers of one tenant half, so a second peer is still served after one peer sends hundreds of refused requests, while a single busy peer is not capped while the table has room. The tenant share applies only while other tenants' or untenanted peers hold entries, and the values are fixed. A full capability probe table or share on the sending gateway now answers the caller 429 with Retry-After 5 instead of 502. The listener also admits Opens off its reader loop, at most 16 at a time, holding up to 8 early frames per stream until its Open is admitted or its admission ends, so a slow admission no longer stalls every other message.
- **End running Fabric streams when a peer's access is revoked** — Running framed streams kept going after a peer left active or was removed, a surface was un-exposed, or a Connection Point was disabled, and a disabled Connection Point still admitted new streams until its listener restarted. A gateway or Connection Point write through this node now ends, at once, only the streams a narrowing change no longer allows. A change picked up from shared storage, or a write that cannot read the record it replaces, ends the running streams the stored records no longer admit. An Open admitted while a revocation runs is refused, and admission reads the Connection Point's current record.
- **Resolve did:web in VP and VC verification through the host-policy resolver** — Presentation and credential verification resolved `did:web` with a resolver that had no host policy and followed redirects, so a presentation naming a DID on a private host made the gateway fetch it. `did:web` now goes through the shared resolver, the same as `did:webvh`, and is refused on non-public hosts unless `[did_cache] allow_private_hosts` is on.
- **Scope and validate the acceptor mediator selection** — `acceptor_mediator_id` goes through the same tenant and resource-scope check as every other mediator lookup, and the new gateway's tenant must be allowed to reference the mediator, as for connection points: a tenant gateway may use its own tenant's mediators or global ones, a global gateway only global ones. An unknown mediator, one outside the caller's scope and one the gateway may not reference get the same 400, so a scoped caller cannot learn that it exists. An in-scope mediator that is disabled, unregistered or has no usable endpoint gets one generic 400 that names neither the mediator nor its state; the detail is logged server-side. Finalize, recovery and the permanent connection point's listener use only the mediator record validated at accept time, by id: the connection point stores that record id as its `mediator_id`, so another tenant's record with the same DID is not used for it, and deleting the mediator stops its listener. Finalize, like recovery, fails if that record has been deleted, given another DID or disabled since the invitation was accepted. On the acceptor's cache-miss recovery path, a recovered mediator other than the temporary connection point's own must be that record, still Active, and recovery fails closed without it or without a mediator store. Shared-mediator recovery needs no registered inviter mediator.
- **Keep mediator send errors out of fabric forward responses** — When a fabric ForwardRequest fails to send, every client-facing path (the inbound fabric proxy, outbound fabric forwards, A2A agent-card fetches and x402 payment delegation) returns a generic message. The underlying SDK or mediator error is logged only.
- **Keep send and lookup errors out of gateway management responses** — Connection setup, ping, retry ping, surface discovery and the acceptor mediator lookup now return a generic message when the send or lookup fails, and log the underlying error server-side instead of returning it to the client.
- **Refuse tenant and resource-scoped tokens reading user and identity mappings** — GET /v1/users/integrations and /v1/identities/integrations returned the appliance-wide mappings, custom variable values included, to any caller with integrations.view, so a tenant or resource-scoped token could read what it may not change. Both now return 403 to such tokens before touching storage, like the PUT routes.
- **⭐ Keep the primary administrator's role across SAML sign-ins** — Every SAML sign-in overwrote the stored role with the identity provider's, so the primary administrator, made Administrator on first sign-in, was demoted to User on the next sign-in whenever the identity provider sent no administrator role. The primary administrator now keeps the role, and a sign-in that would have changed it logs a warning.
- **Refuse integration API requests when no RBAC guard is mounted** — The /v1/integrations routes were served without any permission check when the router was built without an RBAC guard, while neighbouring admin routes refused such requests. They now fail closed with 403. Deployments always mount the guard, so this is hardening against a future wiring change.
- **⭐ Validate user and identity integration mappings before saving them** — PUT /v1/users/integrations and /v1/identities/integrations saved any payload. They now refuse tenant and resource-scoped tokens (403), unknown, tenant-owned, audit or wrong-category integrations, unknown or missing event types, duplicate or excess entries, non-custom or oversized variables and unknown fields (400), and log each accepted change. The routes refuse every request when mounted without an RBAC guard.
- **Skip tenant-owned integrations when sending appliance-wide user events** — User events describe every user on the appliance, so an integration owned by a tenant no longer receives them, even if a stored trigger configuration names it.
- **Fill integration template placeholders in a single pass** — A substituted value was scanned again for placeholders, so a self-chosen username such as ${_TOKEN} could pull an operator's custom variable into the message. Values are now inserted literally.
- **⭐ Stop sending passkeys and profile details in user integration events** — User events (created, approved, updated, deleted, login, accessed) put the whole user record into OLD_STATE and NEW_STATE, including passkey credentials, the SAML subject, email, names, department, job title and avatar path. They now carry only user_id, role, status, is_primary, created_at and updated_at, and trigger logs name the user by id instead of username.
- **Log a capped Fabric MCP initialize revision only when it is a date** — When Fabric receive rewrote a legacy MCP initialize to a served revision, it logged the caller's requested protocolVersion as sent, at info level and with no length limit. It now logs it as the direct Access Point and Transit Points already did: the value only when it is a well-formed date revision, otherwise only its length.
- **Stop logging forwarded header values and bodies on Fabric requests** — When a gateway forwarded a Fabric request to its Target, it logged every forwarded header with its value at info level, including a delegated access token in `Authorization` or in a custom credential header. The sending gateway did the same for the response headers it received back from its Fabric peer, such as `Set-Cookie` or `WWW-Authenticate`, and also logged the whole `ForwardResponse`, header values and body included, at debug level. The info logs now carry only header names, and the debug log only the response status, header names and body size, so no credential value reaches these logs.
- **Block tools/call without a readable tool name on every MCP tool gate** — Only Transit Point gating refused a `tools/call` with no `params.name`, or one whose name was not a string. Every other gate checked it as an empty name, which a deny-pattern gate passes, so an upstream that accepted such a call could reach a hidden tool. The direct Access Point, the `fabric://` send leg, the `proxy://` MCP proxy path, Fabric receive and Transit Points now all deny it when tool gating is configured and record a deny decision. Surfaces and Transit Points without gating are unchanged.
- **Refuse MCP POST bodies that are not one JSON object** — A legacy MCP POST whose body the gateway could not parse as JSON, such as a JSON-RPC batch preceded by a UTF-8 byte order mark, was forwarded without tool gating or tool-scoped credential checks, because the gateway found no tool call in it. An upstream with a lenient parser strips the mark and runs every call in the batch, including a tool the gating hides. Access Points, Transit Points, Fabric receive and the standalone MCP Proxy now refuse, before any tool-level control, an MCP POST body that is not one JSON object. They answer with the JSON-RPC errors the Access Point already returned for malformed bodies: `-32700` for a body that is not valid JSON and `-32600` for JSON that is not an object. Other methods cannot carry a body; see "Refuse MCP requests that skip POST admission by method".
- **Refuse MCP POST bodies with duplicate or case-variant keys** — The gateway kept the last of two duplicate JSON keys but forwarded the original body, so an upstream parser that keeps the first could run a different method or tool from the one tool gating and tool-scoped credentials checked. Go's `encoding/json` also matches field names case-insensitively, so `Name` next to `name`, or a lone `Method` or `params.Name`, had the same effect. Access Points, Transit Points, Fabric receive and the standalone MCP Proxy now refuse with JSON-RPC `-32600` an MCP POST body with two keys of one object, at any depth, that are equal or differ only in case. They also refuse a lone case variant of a field the gateway reads: `jsonrpc`, `id`, `method`, `params`, `params._meta`, `params.name` and `params.arguments` of a `tools/call` or `prompts/get`, and `params.uri` of a `resources/read`. Keys inside tool arguments are not case-checked. A legacy request gets HTTP 200 with `id` null. A `2026-07-28` request gets HTTP 400 with the same code, as for any other malformed modern request, and its `id` echoed unless the `id` key itself is duplicated or a case variant.
- **⭐ Require a per-route opt-in before delegated credentials cross Fabric** — A surface with `outbound_credentials` sent the caller's delegated access token to a `fabric://` peer with no separate control: on modern MCP requests through its Target, and on any request through a `fabric://` Transit Point, including A2A requests that carry it as a header. The token now crosses only when that Target or Transit Point sets `fabric_delegated_credentials: true`, and only for that route. With the setting off, the caller's own token is still stripped and the peer gets no delegated credential. The refresh token never crosses Fabric. A Target variant can override the setting, and a `complete` variant that omits it turns it off. A Transit Point that relies only on its own `transit_credentials` is gated the same way.
- **Stop Transit Points from sending another Transit Point's credentials** — On a surface without `outbound_credentials`, a request through one Transit Point picked up the `transit_credentials` of every Transit Point on the surface, so a token meant for one destination could reach another. A Transit Point now uses only its own `transit_credentials`. This also changes `https` Transit Points, which previously received the other Transit Points' tokens too.
- **Stop sending Transit Point credentials to the surface's Target** — On a surface without `outbound_credentials`, a legacy MCP or A2A request through the Access Point injected the `transit_credentials` of every Transit Point into the request to the surface's Target. The Access Point now uses only the surface-level `outbound_credentials`.
- **Send no delegated credential when a Transit Point variant fails to resolve** — A legacy request whose Transit Point variant cannot be resolved still falls back to the base surface, but no longer carries a delegated credential, so a broken variant cannot send the base surface's tokens to a destination the variant did not intend.
- **Apply MCP tool gates that read the caller DID or payment on Fabric routes** — On a fabric:// target, the MCP tool gate's policy input left out the caller's extension identity, and so input.agent.did, and the payment context. A Deny gate whose condition read them switched off, so its tools were listed and callable over Fabric while the same gate blocked them on a direct target, and an Allow gate hid every tool it grants. The input now carries both, as on the direct path.
- **Keep Transit Point credentials on their own upstream after API changes** — After a Transit Point was removed through the API, the next dashboard save gave its credential and its elements to the Transit Point that took its place on the canvas, and saved that Transit Point twice. A credential or a Fabric delegated credentials switch removed through the API also came back from the canvas layout data. The dashboard now matches each Transit Point to its canvas node by its id, does not restore a Transit Point the stored surface no longer has, and takes every stored Transit Point field only from the stored surface.
- **Update quinn-proto to 0.11.19 to fix QUIC denial-of-service advisories** — Bumps the transitive quinn-proto dependency from 0.11.15 to 0.11.19, which fixes five advisories where a remote QUIC peer could exhaust memory (stream reassembly, connection ID retirements, zero-length DATAGRAM frames) or panic the stack (ACK_FREQUENCY minimum ACK delay, zero-length STREAM frames during unordered reads). Restores a passing cargo audit.
- **Update rustls to 0.23.46 to fix TLS advisories** — Bumps rustls from 0.23.45 to 0.23.46, which fixes four advisories where buffered application data could be sent to the outer server after an ECH rejection, Brotli certificate decompression could allocate up to 1 GiB before authentication, an unauthenticated ServerHello could downgrade later connections to classical key exchange, and Debug output of client session values could expose TLS secrets. Restores a passing cargo audit.
- **⭐ Withhold target credentials from callers whose source auth failed** — A caller whose source authentication failed is now forwarded without the stored target credential on `proxy://` MCP Targets, Fabric send, Fabric receive (direct and MCP proxy Targets) and the `a2a-proxy://` Direct Line secret, as the direct inbound path already did. Previously these paths decided from the request path alone or assumed the caller was authenticated, so an anonymous caller on a surface without a denying policy reached the backend with the operator's credential. Agent-card fetches between gateways still carry the receiving gateway's credential.
- **⭐ Refuse tenant token writes to appliance-wide management records** — A tenant access token can still read records that belong to no tenant, but now gets 403 when it updates, deletes or otherwise changes them in JWT verification strategies, secrets, STS clients, mediators, credential providers, certificates, trust authorities, issuers, trust registries, surface templates and integrations (including triggering an appliance-wide integration), and on the appliance Gateway's Connection Points, which tenant tokens can therefore no longer create. Previously these write paths used the read rule, so a tenant could, for example, replace a global JWT strategy's keys. Tenant automations that edited untenanted records need an appliance-wide token, or an operator can assign the record with `PUT /v1/tenant-ownership/...`.
- **Refuse to start when source authentication cannot initialise** — A gateway in Active or Standby mode now exits at startup if the JWT verification strategy store cannot be opened, instead of running with source authentication silently disabled and attaching target credentials for every caller. A Fabric message that reaches a surface with caller authentication before source authentication is ready, or a direct request on a surface whose source authentication is missing, now gets 500. A fresh install is unaffected, because the store directory is created on first start.
- **Stop logging integration credentials and webhook URLs** — The integration test endpoint no longer logs the submitted configuration or content, and Slack, webhook and Redis Streams publishers no longer log webhook URLs, Redis connection strings or URLs inside HTTP errors, which can carry passwords and bearer tokens.
- **Accept one connection setup per gateway invitation, and only that one** — A gateway invitation now accepts a connection setup only on a User Connection Point with a secret, only when the setup's parent thread id names the invitation message the mediator served, and only once. Previously the parent thread id was ignored, a leaked invitation URL and secret could be redeemed repeatedly until it expired, and system Connection Points with an empty secret accepted setups, each one creating an approval request, an admin notification and integration calls. The secret is now compared in constant time, and a setup that fails after its secret is accepted, such as at the appliance gateway limit, leaves the invitation unused so the peer can retry.
- **Answer 404 for records a tenant token cannot see on every write** — Updating, deleting or otherwise changing another tenant's record now returns the same 404, with the same body, as a missing record across all management stores, Gateways, Connection Points, Agent Surfaces, policies and API keys, so a tenant token cannot tell that an id exists in another tenant. Secrets, certificates and API keys outside the token's resource pattern answer the same way. A record the token can see but not change, such as an appliance-wide one, still returns 403. Previously these writes returned 403 for another tenant's record.
- **Publish the Docker Compose ports on loopback only** — docker-compose.yml now publishes the HTTPS (8443) and HTTP (8080) listeners on 127.0.0.1 instead of every host interface, so a local gateway is not reachable from the network before its first administrator registers. Remove the 127.0.0.1 prefix to expose it deliberately.
- **Cap Legacy SSE sessions at 10,000 and answer further GET /sse with 429** — GET /sse on proxy:// and fabric:// surfaces and on standalone MCP proxies created a session with no limit, so a client could open sessions until memory ran out. The gateway now holds at most 10,000 Legacy SSE sessions, matching the Streamable HTTP notification stream cap; sessions whose client has disconnected are dropped first, and a request beyond the cap gets 429 "Too many active SSE sessions".
- **⭐ Verify x402 payments against the surface's configured requirements** — x402 verification now requires a credential's `accepted` object to name one of the payment requirements the surface issued, exactly in scheme, network, asset, recipient, amount, asset transfer method and EIP-712 domain, and rejects it in every verification mode otherwise. Signature, on-chain and facilitator checks take their expected values from that requirement, embedded and external facilitators receive it as `paymentRequirements`, and the transaction record and settlement use it. Previously a credential was checked only against its own `accepted` object. Deferred settlement records written by earlier builds settle only if they still name one of the surface's current requirements, and are marked failed otherwise.
- **Enforce access-token scopes on the JWT verification strategy routes** — The /api/v1/jwt-verification-strategies routes (list, get, create, update, delete and validate-jwks-uri) now also require the matching jwt_verification_strategies feature in a scoped personal access token's scopes, instead of checking only the owner's role. Session logins and tokens without feature scopes are unchanged.

The effective ceilings double: one peer can hold 16 inbound streams and one surface 32. The total of 128 streams per direction still counts both.
- **Log which Fabric stream cap refused a stream and for which peer** — A stream refused by a full Fabric cap is logged at `warn` as `Fabric stream cap reached` with the peer DID, surface, stream kind, direction and which cap was hit (`total`, `per_peer`, `per_surface` or `open_replay`), and the receiver's `Rejecting Fabric Open` warning carries the sending peer's DID, so refusals for one partner can be traced. A refused Open left unanswered because 16 refusals are already awaiting an answer is now logged at `warn` instead of `debug`.
- **Register a modern-only catalog when the legacy OpenAPI converter fails** — An MCP Proxy whose OpenAPI spec the legacy catalog converter cannot load now registers a modern-only catalog instead of failing, and its request body limit always comes from `mcp_http`. Its create and update responses carry a `warnings` entry naming the converter error, because `2024-11-05` clients of that Proxy get `500`; the dashboard's create wizard and edit page display those warnings. Updates that do not rebuild the catalogs still return the warning until a rebuild loads the legacy catalog. Management tool discovery reads the modern catalog, so it lists that Proxy's tools instead of returning `500`.
- **Trust the sending gateway's Origin check on buffered Fabric receive** — A buffered Fabric `ForwardRequest` no longer rechecks the caller's browser Origin against the receiving surface's `mcp_http.allowed_origins`, so a legacy browser client admitted by the sending gateway is not refused with `403` by its peer. Header and body limits still apply, with the forwarded Origin counted toward the header budget, and framed streams still check Origin on receive.
- **Restrict the Fabric Origin-check bypass to the receive path** — The Origin-check bypass is now limited to the buffered Fabric receive path, so regular HTTP policy handling continues to enforce configured origin allowlists.
- **Document modern MCP admission and rollback behavior** — The documentation now describes modern MCP admission on every endpoint, the retired protocol setting, and the steps required before downgrading to an older release.
- **Close every MCP subscription on the vault when one consent epoch read fails** — One unreadable, timed-out or corrupt consent-epoch read now ends every MCP subscription on the appliance's delegation vault within the recheck interval, where before it ended only the stream that made the read. The vault is shared across surfaces and tenants, so a single throttled or slow kms:Decrypt closes all subscriptions; each such read is counted in agent_gateway_mcp_subscription_epoch_unavailable_total so correlated mass closes are visible.
- **End legacy MCP SSE passthroughs at the surface's stream idle and lifetime limits** — A legacy MCP text/event-stream passthrough now ends when the upstream sends nothing for the surface's mcp_http.stream_idle_timeout_secs (default 60 s) or is still streaming at mcp_http.stream_max_lifetime_secs (default 3600 s), as modern MCP streams already do. Before, a passthrough could stay open indefinitely. Surfaces whose upstream is quiet for longer than 60 s between events need a larger stream_idle_timeout_secs.
- **Document x402 payment requirement binding** — Documents configured requirement binding, facilitator behavior, settlement handling, and the test-only nature of mock verification in PROTOCOLS.md, ARCHITECTURE.md, and CONFIGURATION_REFERENCE.md.
- **Document token-scoped permissions** — Updates the RBAC guide with personal access token scope behavior for permissions and JWT verification strategy routes.

### Fixed

- **Reject an access token secret rotated while its request was being authenticated** — A request that presented a token's old secret and was still being authenticated when a rotation replaced that secret is now refused with 401, instead of being let through once. A token revoked or expired in that window is refused the same way.
- **Audit requests denied because a policy could not decide** — When a gateway, access-point inbound, surface or MCP tool policy raised an evaluation error, had no policy engine, or was enabled without a compiled policy, the request was denied without a policy decision record. These denials are now recorded with decision error and deny_reason evaluation_error, no_policy_manager or policy_not_compiled, on the direct, Fabric and MCP-proxy paths.
- **Audit trust checks that failed on an unavailable A2A proxy agent card** — When an A2A proxy target's agent card could not be synthesized, its target-leg trust checks failed with AGENT_CARD_UNAVAILABLE without a trust_check audit record or metric. They are now recorded like the same failure on the outbound path.
- **Keep delegation audit records when a request ends before its VP is minted** — Credential delegation records held back until the request's identity VP was minted were lost when the request returned early, for example with 503 when delegated credentials were unavailable. They are now recorded without a VP on every path.
- **Send Retry-After when an Access Point rate limit refuses a request** — A request refused with 429 by an Access Point rate limit now carries a Retry-After header; it was never set.
- **Keep the audit pipeline running when its journal or cursors are damaged** — An unreadable line at the end of the audit journal, or an unreadable cursors.json, stopped the audit pipeline from starting, so the gateway kept serving with no audit records kept or forwarded until restarted with the file repaired. An unreadable line elsewhere in the journal stopped every sink behind it for good. On start the journal is now cut back to its last readable line and an unreadable cursors.json is renamed to cursors.json.corrupt-<unix seconds>; readers move past unreadable lines and count them in agent_gateway_audit_sink_skipped_total with reason corrupt. agent_gateway_audit_pipeline_started reports 0 when the pipeline could not start.
- **Pause a disabled Governance Audit integration without replaying old records** — Records addressed to a Governance Audit integration that was disabled, given a tenant or moved to another category were passed over as delivered until its delivery stopped, and its undelivered records could later be deleted uncounted or replayed when it was re-enabled. A paused or deleted Governance Audit integration now receives nothing. Its undelivered records are let go and counted in agent_gateway_audit_sink_skipped_total with reason paused, with one warning per integration, and a deleted integration's position is dropped. Resuming continues from the pause, so only records produced after it are delivered. Until delivery stops, each record it refuses is counted in agent_gateway_audit_forward_total with result not_receiving rather than reported as delivered. Records produced at the moment of pausing may still be delivered after it resumes, or be counted as paused.
- **Record x402 settlements that fail immediately** — An immediate x402 settlement that returned an error without marking itself failed left the transaction without a settlement failure. It is now marked failed and recorded once as a failed payment event.
- **Run the governance audit pipeline only on the Active node** — A Standby node also started the audit pipeline, so in a failover pair sharing storage both nodes could open the same journal, write records with the same sequence numbers and overwrite each other's cursors, and a promoted node continued from a stale position. Only the Active node now runs the pipeline. Stepping down journals what was handed over, stops delivery and releases the journal; becoming Active re-opens the journal and cursors from disk and continues after the last record. The journal holds an exclusive lock, so a second writer cannot open it, and a node that becomes Active while another still holds it tries again every 5 s. agent_gateway_audit_pipeline_started is 0 on a Standby node.
- **Retry rebuilding the audit sinks when integrations cannot be listed** — When the integrations could not be listed, the previous audit sinks were kept until the next settings or integration change, so a just-disabled integration could keep receiving records. The rebuild is now retried every 5 s until it succeeds and each failure is counted in agent_gateway_audit_sink_rebuild_failed_total. Rebuilds also run one at a time, so a slower rebuild can no longer replace newer sinks. A rebuild before integration storage is set up counts as a failed listing rather than as no integrations.
- **Re-read the audit journal after a failed append that could not be undone** — When appending to the audit journal failed and the partial batch could not be cut off again, the next batch was written after the partial line. The segment is now re-read before the next append, as on start, so no partial line is left behind and no sequence number is reused.
- **Build the audit sinks before the audit pipeline starts** — The audit pipeline started before the Governance Audit integrations were loaded, and a node becoming Active kept the sinks it had built before, missing integration changes made on the other node. The sinks are now built from the current settings and integrations every time the pipeline starts, on start-up and on becoming Active; while the integrations cannot be listed the pipeline waits and tries again every 5 s.
- **Stop every audit pipeline job when a node steps down** — A node stepping down waited for the audit journal writer, which kept retrying a failing journal, then aborted the dispatcher while its readers kept delivering and saving cursors on their own. Stepping down now gives the writer up to 5 s to journal what it was handed, then cancels the writer, the dispatcher and every reader, dropping any delivery in flight; records still unwritten are counted in agent_gateway_audit_records_lost_total with reason aborted. No cursor is saved afterwards, and the journal lock is released only once every job has stopped. Waiting to take over the journal and retrying a failed sink rebuild also end on stepping down. A writer stuck inside a disk write keeps the lock and an error is logged; the node must then be rebooted.
- **Forward audit records with current settings after becoming Active** — A node promoted to Active kept the dashboard settings it loaded at boot and its cached integrations, so it could keep the VP Audit Log selection or send to an integration as configured before the other node changed them. On becoming Active the node now re-reads the settings from disk and empties its integration cache before the audit pipeline starts, so the sinks and every delivery follow what is stored now. The node still admits traffic after one start attempt and keeps retrying a refused start in the background.
- **Count only Governance Audit integrations that receive events on the Audit Log** — The Audit Log's "Forwarding to N integrations" counted every active appliance-wide Governance Audit integration, including ones that select no events and so receive nothing. It now counts only those that select at least one event, and shows a warning naming how many select none. With VP Auditing off it no longer adds "(VP Auditing off)" or says nothing is forwarded; its tooltip says the VP Audit Log keeps nothing while integrations still receive the events selected for them.
- **Describe how Governance Audit integrations receive audit records** — The Audit Log's About panel said every entry is sent to Governance Audit integrations and that forwarding is best-effort. It now says the log keeps the events selected under Settings › Security › VP Audit while VP Auditing is enabled, that each integration receives the events selected for it independently of the log, and that delivery is at least once, so receivers deduplicate on event_id. The Governance Audit card on the integration pages, which said records are skipped only past the backlog cap, now also says that disabling an integration pauses it and lets go of what it has not received, and that once re-enabled it receives only new records.
- **Stop the BDD Gherkin linter rejecting valid Cucumber Expressions** — scripts/bdd-gherkin.py only understood parameters in Cucumber Expressions, so valid bindings using optional text such as request(s) or an escaped slash were reported as unused and their steps as unmatched, failing the BDD Gherkin lint. It now understands escapes, optional text, alternation and the int, float, word and string parameter types as cucumber-rs does, and reports a binding whose expression cannot be parsed, or whose regex does not compile, with the reason.
- **Stop signing an identity VP for agent card responses** — Inbound and fabric receiving gateways no longer sign a backend agent VP for public or extended agent card responses, which have nowhere to carry it, removing a wasted signing and a misleading warning on every card fetch.
- **Pull G2G BDD images from workflow version variables** — Fix the gateway-to-gateway CI image pre-pull step by using explicit mediator and Valkey version variables.
- **Stop checks workflow failing at startup on every job** — The workflow-level permissions block caps every job at contents: read, but the audit job's reusable workflow needs issues: write to annotate RustSec issues. That mismatch failed the entire checks workflow at startup, so fmt, clippy, cargo-deny and rust-scan never ran either; the audit job now declares its own permissions to cover this.
- **Restrict publish to release-PR merges and recoverable re-runs** — The publish workflow now only runs for commits that merge a release/vX.Y.Z branch, so an unrelated push to main touching Cargo.toml or CHANGELOG.md (such as a Dependabot merge) can no longer trigger a release. It also checks out the exact triggering commit instead of main's tip, so the built binary always matches the tagged commit, and re-tagging is skipped when a prior run already tagged that same commit.
- **Let the reviewed release flow publish an untagged current version** — Prepare release always bumped forward from the version in Cargo.toml, so it could never produce the first release if that version was already set but never tagged. It now releases the current version as-is when it has no matching tag yet, and only bumps once that version has been published.
- **Explain RustSec findings in the audit job** — The local audit job now prints advisory IDs, affected packages, versions, and remediation URLs while preserving cargo-audit's failing exit status.
- **Handle annotated tags when retrying a release** — Compare release reruns with the peeled commit SHA so annotated tags are recognized as pointing at the expected commit.
- **Preserve release ordering and first-release notes** — Place dated releases after the Unreleased section and merge any undated same-version changelog stub into the new release notes.
- **Reject duplicate changelog YAML keys** — Use a shared YAML loader that rejects duplicate mapping keys so release entries cannot silently disappear before validation or rendering.
- **Give Fabric extended-card tests a larger stack** — Run the deep Fabric extended-card proxy tests on an 8 MiB stack to prevent stack overflow in CI unit and coverage jobs.
- **Keep other Identities rows expanded when a row is expanded via its link** — Expanding an identity row on the /identities/:did route no longer collapses rows that were already expanded.
- **Stop Trust Recorder custom resource inputs squeezing the selects** — In the Trust Recorder editor, the Action and Resource inputs of a custom resource row now share the remaining width and can shrink. Entity Target and Record Type keep fixed widths, and every column has a label so the row lines up.
- **Record an Issuer's own DID when it is chosen as Trust Recorder authority** — Choosing an Issuer in the Trust Recorder Authority dropdown stored the authority the Issuer was registered under, often the gateway's DID, so records showed the gateway as the authority. It now stores the Issuer's own DID. Entries saved with the old value show as Custom until re-selected.
- **Reconnect a Connection Point whose account the mediator has lost** — A mediator can lose accounts while connections stay open, for example when its store is flushed or fails over. It recreates an account only when that account sends and refuses delivery to a missing one, so a gateway that only received stayed unreachable until it sent, restarted or was reconnected by hand. Every connected Connection Point now checks its own mediator account every 30 seconds, four at a time, reauthenticates and reregisters when the account is gone, and re-opens the receive list, within 10 seconds, when it was closed. An account that cannot be read on consecutive checks is logged at warn, and a Connection Point stopped or removed while it is checked is not started again. The Gateway Ping timeout uses the same check.
- **Keep concurrent first Fabric stream requests to one peer from failing** — When several first requests to a peer negotiated stream capabilities at once, a later disclosure replaced the earlier agreement and the request still waiting for it failed, and a burst of first requests could use up the peer's share of the receiver's offer table. Concurrent first requests to a peer now share one capability query and all get its answer for up to 5 seconds, after which the next request sends a new query; a query that cannot be sent fails them at once, and a request keeps the agreement negotiated for its own query when a later one replaces it.
- **Restart the Connection Point when the mediator reports its account missing** — After a gateway ping timed out, the account probe's `e.p.account.not_found` problem report went back to the probe itself, never reached the listener, and the Connection Point stayed on a dead mediator session. The ping handler now restarts that Connection Point's listener so it re-authenticates and re-registers. It matches the exact code, and it restarts only the listener instance it probed, so concurrent pings do not tear down a session another one just restored. A stored mediator DID document is also cached before the messaging profile is built, so the profile finds its mediator at start.
- **Refresh mediator functions after an EC2 redeploy** — EC2 mediator redeploys now refresh the bundled Redis functions before starting the mediator, so upgrades do not retain stale functions or report a degraded readiness state.
- **Keep a new access token link and its presets across sign-in** — Opening a /access-tokens/new link while signed out landed on the dashboard root after SAML login, because the return target was limited to the root and the CLI authorize path. The login page now carries the form and its re-encoded query as the return target, and the gateway's SAML return-target allowlist accepts /access-tokens/new. The form is only prefilled, never submitted.
- **Stop offering invalid departments.* scopes for access tokens** — The permissions endpoint no longer emits the legacy departments.* aliases. The token form built its scope list from that map, and creating a token with one of them failed with unknown scope because the RBAC loader normalises them to issuers.*.
- **Resolve connection-point mediator endpoints from the mediator's DID document** — The inviter's approve flow and the acceptor's finalize and recovery paths used to guess an https origin from the mediator DID string, which is wrong for plaintext mediators and for mediators whose endpoint has a path. They now prefer the stored mediator DID document. When the acceptor shares the inviter's mediator and has no record of it, it uses the mediator URL from the OOB invitation. A failed mediator store read during finalize is logged before falling back.
- **Report unreadable integrations as server errors when saving mappings** — Saving gateway, user or identity integration mappings turned any failure to load a referenced integration, including a corrupt or undecryptable record, into a 400 saying the reference was not accessible, with nothing logged. Unknown or malformed ids still get that 400; a record the store cannot read now gets a 500 and is logged with the integration id.
- **Stop startup on an invalid integration variable pattern** — An invalid integration.variable_pattern was silently ignored for substitution but crashed template validation later, and a failed lock read delivered placeholders as literal text with no log. The pattern and custom prefix are now fixed once at startup, an invalid pattern stops the gateway with a clear error, and every reader uses the same compiled pattern.
- **Show integrations that can no longer be attached so they can be removed** — A stored mapping whose integration was deleted, re-categorised or given a tenant was invisible on the integration pages but still sent on save, so the user and identity pages could not be saved once the API began refusing such mappings. These now show as NOT AVAILABLE rows with a Remove button and block Save until removed, and the selector offers only integrations the page can attach.
- **⭐ Attach an integration to events as soon as it is selected** — Choosing an integration on the gateway, connection point, user and identity integration pages did nothing, so Save stayed disabled and no events could be wired up. Selecting one now attaches it with its template's custom variables, opens it to choose events, and removes it from the selector.
- **Show load and save failures on user and identity integration pages** — Both pages reported a failed save as success and showed a failed load as an empty list that could then be saved over the stored mappings. Failures now show the server's message, and a failed load offers no editor.
- **Require an event for each integration on user and identity pages** — Save stays disabled until every attached integration names at least one event, matching the API, and missing custom variables are checked against the integration's template.
- **Give the fabric tools/list gate the caller identity it decides on** — An MCP tool gate whose condition reads the caller - anything under input.source_auth - could never match when tools/list was answered over the fabric leg: that filter built its policy input without the caller's source authentication, so the condition was unknowable. An unknowable condition forces an Allow gate inactive, so under a deny-by-default gating config every tool the gate would have granted was hidden, with no error and an empty tool list. The filter now carries source_auth and identity_binding and normalizes the caller DID, exactly as the tools/call gate on the same leg already did, so a tool shown in the list is the one the call gate admits.
- **Fix storage backups failing restore with duplicate manifest entries** — Backups taken from storage that contained a legacy backup manifest file under META-INF carried two manifests and failed to restore with "backup contains duplicate manifest entries". Restoring a backup whose manifest uses the legacy name could leave that file in storage. Backups now skip stray manifest files and log that they can be deleted, restores never write either manifest name into storage (including dot-segment variants of the name), and an archive carrying both manifests is validated against the current one, so backups already taken this way restore again.
- **Keep the canvas Entry point URL copy button visible and clickable** — With a long URL on a canvas that was not wide enough, the URL banner at the top of the Surface Builder slid under the canvas toolbar, so its copy button sat beneath the disabled Undo button and could not be clicked, or was pushed out of the banner. The variants widget, the banner and the toolbar now share one row along the top of the canvas, so the banner shrinks to the space between them and only its URL text is truncated. Copying uses the shared copy button, and a refused copy, for example on a plain-HTTP origin, now shows an error toast instead of failing silently.
- **Apply tool-scoped credential bindings only to tools/call on Access Points** — An Access Point matched `required_for.tools` against `params.name` of any legacy MCP method, so a `prompts/get` whose name equalled a listed tool picked up the tool-scoped credential. Only a `tools/call` now names a called tool; the `input.mcp.tool_name` policy input is unchanged.
- **Apply tool-scoped credential bindings on Fabric receive** — Fabric receive passed no tool name to credential delegation, so a binding with `required_for.tools` on the receiving surface never applied. It now matches `params.name` of a `tools/call`, read after admission has refused batches and ambiguous keys, because Fabric receive forwards only to its own Target. Upgrade note: such a binding now sends the delegated credential to that Target for the listed tools, or asks for consent when no credential is stored.

The Surface Builder now accepts the credentials in the shape they are loaded in, so every Transit Point on the canvas is saved. It also keeps a stored elicitation timeout and fallback, which a save used to reset to 300 seconds and on_demand.
- **Keep explicit empty or zero retry values when saving from the dashboard** — Saving a surface from the dashboard dropped an empty list of retryable status codes, so the gateway fell back to its default codes and retried calls on 5xx that the operator had limited to connection errors. Zeros for retry attempts, the circuit-breaker failure threshold and its timeout were saved as 3, 5 and 30. The dashboard now keeps these values as stored. An empty list shows as a new Retry on connection errors only switch, an empty codes field still means the gateway default, and input that is not a list of HTTP status codes blocks Save instead of being saved as an empty list.

The dashboard now takes Networking settings only from the stored surface, for the Target and for each Transit Point.
- **Run the MCP conformance harness on Node 22** — The pinned @modelcontextprotocol/conformance suite imports fs.globSync, which only exists in Node 22 and newer, so every conformance scenario crashed on load in CI under Node 20. The CI conformance job now uses Node 22, and the harness preflight, package engines and docs require Node 22 or newer instead of 20.18.1.
- **End only the MCP subscriptions on the changed surface or tenant** — Saving or deleting one surface, or changing its surface policy, now ends only the open MCP subscriptions on that surface, and changes to a tenant's MCP proxies, JWT verification strategies or credential providers end only that tenant's subscriptions. Previously any of these ended every open subscription on the gateway, so one tenant's configuration writes disconnected every other tenant's subscribers. Gateway and global policy changes, API-key changes, delegation vault revocation, JWT strategy reload, policy updates on surfaces with a response policy (whose engine is shared by definition) and changes to appliance-global or re-owned resources still end every subscription. - **Show one save button and an honest value reveal in the secret editor** — The secret editor had two save buttons and a reveal toggle that showed an empty field, because stored secret values are never returned by the API. The editor now has a single save button, marks the stored value as hidden, and offers the reveal toggle only for a value entered or generated on the page. - **Read each vault's consent epoch once per second for all its subscriptions** — MCP subscriptions on the same delegation vault now share one consent-epoch watcher instead of each re-reading the epoch every second, so vault reads (and kms:Decrypt calls with the aws_kms backend) no longer grow with the number of open subscriptions. A changed epoch ends the subscriptions started under an earlier one. A subscription whose epoch differs from the watcher's last reading reads the epoch once more before joining, so one started under a newer epoch, or after the vault recovers, is not closed by a stale reading. The watcher stops when the last subscription on the vault closes.
- **Count MCP SSE streams as active connections until they end** — Legacy MCP SSE passthrough responses, legacy GET /sse streams on proxy:// and fabric:// surfaces, and the Streamable HTTP GET notification stream now hold their connection guard until the response body ends or the client disconnects, as modern MCP streams already did. Before, the guard was released when the response headers were sent, so running streams were missing from the active-connection metrics.
- **Keep idle long-lived streams in the active-connection count** — The task monitor no longer resets a task's active connections to zero after two minutes without activity. Every request's connection guard releases its count when the request or stream ends, so the reset only hid quiet streams and listens from the dashboard, Prometheus, CloudWatch and OpenTelemetry active-connection gauges.
- **Drop connections and streamed responses without panicking outside the runtime** — Dropping a connection guard, or any streamed MCP response body (legacy or modern), outside a Tokio runtime, for example during shutdown, no longer panics. A modern response's completion bookkeeping (connection count, bytes, errors, metrics) is skipped with a warning instead of spawning a task, and a guard leaves its count as is. The element now reads the stored timeout, retry (including retryable status codes), circuit breaker and mirror settings into the panel, on the surface and on each transit point. Settings that are not stored stay off; no defaults are filled in.
- **Keep a surface's Target Networking settings when saving it after a reload** — After a surface was reloaded in the dashboard, its Target Networking element sat ahead of the Target on the canvas, and saving the surface left out `target.networking`, so the timeouts, retries, circuit breaker and mirror stopped applying. This happened whether Networking was set in the dashboard or through the API. The element is now saved wherever it sits on the Access Point to Target edge.
- **Limit /api/v1/permissions for access tokens to the token's own scopes** — A personal access token now sees only the features its scopes grant, capped by its owner's role, instead of the full role. The response is also sent with no-store and Vary Authorization, Cookie so it is not cached across credentials.
